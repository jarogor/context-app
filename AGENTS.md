# AGENTS.md — правила разработки Контекста

Правила относятся к Rust-коду (`src-tauri/`) и организации проекта. Их нужно
соблюдать при любой правке, чтобы структура оставалась предсказуемой.

## Именование служебных имён

Единая нотация для имён, которыми владеет приложение: по имени должно быть
понятно назначение объекта, а соседние объекты не смешивают разные системы.

- **Каталоги и файлы приложения — `kebab-case`**: `app-state`,
  `base-plugins`, `app-plugins`, `library-history.json`, `wasm-cache.toml`.
- **Ключи внутри JSON-файлов приложения — `snake_case`**: `added_at_millis`,
  `active_tab_id`, `current_workspace_id`.
- **Идентификаторы плагинов — UUID**: `id` в манифесте, папки состояния
  плагинов.
- **Идентификаторы capabilities — `<домен>.<сущность>@<версия>`**:
  `books-source.catalog@1`, `settings.store@1`.
- **Ключи настроек — точечные сегменты `snake_case`**:
  `startup.welcome_notification`, `appearance.palette`.

Сторонняя нотация (`CacheStorage`, `WebKitCache`, `mediakeys`, `storage`,
`hsts-storage.sqlite` и подобное) допустима только для данных, чьё имя задано
не приложением (движок webview, внешние форматы). Такие данные изолируются в
подкаталог приложения с понятным именем (`app-state/webview`) и не попадают в
корень каталога данных рядом с нашими именами.

## Концепция: каркас, приложение и плагины

- Источник истины по устройству проекта — `CONCEPT.md`: что такое каркас, что
  такое приложение и что такое плагины, как они связаны и как называются.
  Перед планированием и правками сверяться с ним.
- Каркас — обезличенный фундамент, на котором строится любое приложение. Он не
  содержит предметной области: ни книг, ни заметок, ни форматов.
- Всё предметное — приложение и его плагины. Плагины бывают как минимум двух
  типов: **с фронтендом** (в «Контексте» — плагины форматов чтения: EPUB, FB2,
  PDF, DjVu) и **без фронтенда** (интерфейс рисует приложение).
- Плагины самостоятельны и обновляются по частям: они не делят исходный код и
  сборку друг с другом. Связь — только через объявленные права и возможности.

## Планирование и дорожная карта

- Источник истины по направлению, доменам и приоритетам — `ROADMAP.md`.
  Перед планированием и выбором задачи сверяться с ним.
- Текущее состояние функциональности фиксируют `openspec/specs/`, конкретные
  задачи — `openspec/changes/<change>/`.

## Разделение кода по файлам

Код делится на три слоя, и каждый слой живёт в своих файлах:

1. **Структуры и DTO** — только данные, без поведенческой логики:
   - доменные сущности каталога — `catalog/entities/<сущность>.rs`, по одной
     структуре на файл, с переэкспортом из `catalog/entities/mod.rs`;
   - прочие DTO модуля — в `models.rs` рядом с логикой модуля (например,
     `sources/models.rs`, `config/models.rs`, `import/models.rs`).
2. **Логика** — функции и методы работы с данными: `mod.rs` модуля или
   отдельный файл фичи (`scanner.rs`, `index.rs`, `repository.rs`, `schema.rs`).
3. **Тесты** — всегда в отдельном файле, никогда inline в исходнике:
   - `foo.rs` → `foo_tests.rs`;
   - координатор модуля `mod.rs` → `_tests.rs` в папке модуля;
   - подключение через:
     ```rust
     #[cfg(test)]
     #[path = "foo_tests.rs"]
     mod tests;
     ```

Новый код пишем по образцу соседних модулей: `catalog/entities/`,
`import/epub_parser/models.rs`, `plugin/plugin_manifest.rs` + `*_tests.rs`.

## Комментарии

- Все комментарии и документация — на русском языке.
- Doc-комментарии (`///`) обязательны для:
  - каждой структуры и перечисления (и каждого варианта перечисления);
  - каждого поля структуры;
  - каждого метода и функции.
- Модуль начинается с `//!`-описания назначения.
- Комментарии к методу пишутся в дескриптивном стиле («Создание/Обновление/
  Удаление», «Получение…»), а не в императивном.
- Отдельные комментарии — только для неочевидной логики; не комментируй
  очевидное.
- Существующие комментарии при редактировании не удалять.

## Общие конвенции Rust

- Не использовать однострочные `if`/`for`/`while` без блочных скобок.
- Не добавлять комментарии-шум и «мёртвый» код.
- Приватные вспомогательные функции размещать рядом с местом использования.
- Публичные API минимальны: по умолчанию `pub(crate)`.

## Плагинная архитектура

- **Плагин — самостоятельное приложение.** Архитектура плагинов существует,
  чтобы плагины разрабатывались независимо и устанавливались в готовом виде;
  поэтому плагин не делит код, тулчейн и зависимости с приложением-оболочкой и
  может быть вынесен в отдельный репозиторий. Связывать плагин с оболочкой
  общими модулями, конфигами сборки или пакетами нельзя — это убивает
  независимость разработки и установки.
- Функциональность, специфичная для формата каталога, реализуется только
  плагинами (`plugin/`): сторонние библиотеки читаются плагинами источников книг
  (назначение `kind: "books"`) через host-функции `fs_list_dir`/`fs_read_bytes`, а ядро
  оперирует общими моделями из `source-protocol`, не зная их предметного смысла.
- Ядро не знает о конкретных источниках: распознавание корня
  (`probe`), сканирование (`scan`) и починку (`scan_book`) выполняет
  выбранный плагин источника книг.
- **Ядро обновляется целиком, прикладные плагины — по частям.** Ядро — это
  приложение и каркасные плагины (`level: "framework"`); они связаны контрактом
  и заменяются одним пакетом из одного источника (`UPDATE.md`). Прикладные
  плагины (`level: "application"`) обновляются через стор по отдельности.
  Сетевой источник обновлений обязан использовать HTTPS, а сетевые пакеты —
  проверяться по SHA-256; подпись издателя — следующий шаг перед публичным
  сетевым стором.
- Исходники WASM-плагинов живут в workspace `src-wasm-plugins/` (один плагин —
  одна подпапка); переиспользуемые крейты каркаса (SDK) — в отдельном workspace
  `src-wasm-sdk/`. Сборка всех плагинов — `scripts/build-wasm-plugins.sh`,
  поставляемые артефакты — в `src-tauri/resources/plugins/`.
- Общий плагин источника книг «директория книг» живёт в
  `src-wasm-plugins/books-source/` и поставляется в
  `src-tauri/resources/plugins/books-source/`; отдельный источник Calibre —
  `src-wasm-plugins/books-source-calibre/`.
- Каркас приложения держит плагины каркаса отдельно от плагинов приложения:
  app-level `AppPluginHost` грузит плагины уровня каркаса и области приложения из
  `src-tauri/resources/base-plugins/`, а per-library `PluginSession` грузит
  сессионные (источники книг) и книжные (форматы чтения) плагины из
  `resources/plugins/` и `plugins/` библиотеки.
- Host-функции `log`/`notify` только публикуют событие в `plugin::bus`; его
  доставляет app-level runtime плагину, предоставляющему capability
  `notifications.journal@1`. Ядро не хранит журнал и не интерпретирует его модель.
- Host-функция `emit_event(name, payload)` — generic relay прикладных событий
  Tauri; базовые plugins используют её для live-обновления встроенных
  областей приложения.
- Автономные frontend-плагины (`kind: "ui"`, iframe, отдельные сборки) не
  поддерживаются: ядро и оболочка не загружают их. Интерфейс встроенных
  областей принадлежит приложению и собирается из `@context/ui`.
- Базовый плагин уведомлений — `src-wasm-plugins/notifications/`; UI журнала —
  встроенная область оболочки `src/lib/NotificationsPanel.svelte`.
- Базовый плагин настроек — `src-wasm-plugins/settings/`; предоставляет capability
  `settings.store@1` и владеет реестром секций и значений настроек в служебном
  состоянии. Плагин объявляет секции настроек в необязательном поле `settings`
  своего манифеста; секция описывает поля с человекочитаемым названием, типом
  (`boolean`/`string`/`number`/`select`/`json`) и значением по умолчанию. Ядро
  передаёт декларации как opaque-схему и не интерпретирует их. Ядро собирает
  реестр из базовых, сессионных деклараций и собственной секции приложения и
  регистрирует его через opaque-операцию `register`. Интерфейс секций плагин
  отдаёт декларативным деревом `ui-schema` в пространстве `settings.section`
  (операция `ui`), а взаимодействие принимает интентом `{space, id, action,
  values}` (операция `intent`); поля в дерево превращает SDK `ui-sdk`, а рисует
  его рендерер `@context/ui`. UI настроек — встроенная область оболочки
  `src/lib/SettingsPage.svelte`, не знающая о типах полей. Примеры:
  `app.general.startup.welcome_notification` (читает ядро) и
  `notifications.notifications.technical_visible_default` (читает область
  уведомлений).

## Старт приложения и загрузка

- В приложении есть **стадия начальной загрузки (бутстрап)**: `Root.svelte`
  держит фазы `boot → ready | error`, оболочка `App.svelte` монтируется только
  в фазе `ready`, а состояние грузит чистый модуль `src/lib/bootstrap.ts`
  (`loadBootstrap`).
- **Всё, что требует загрузки, выполнять на бутстрапе, а не лениво в процессе
  эксплуатации.** Данные, которые область иначе запросила бы при первом
  открытии (декларации настроек, журнал, каталог стора и т.п.), нужно читать до
  первого кадра и передавать области пропом. Ленивая загрузка даёт
  подвисание при первом обращении к разделу и промежуточный неполный кадр.
- Перед первым рендером состояние должно быть полным: пока грузится — экран
  загрузки, при ошибке — отдельное состояние с повтором, но не пустой и не
  частично готовый интерфейс.
- **Тяжёлая инициализация не должна задерживать появление окна.** `setup`
  выполняется до показа окна: всё, что может занять заметное время (загрузка и
  компиляция WASM, регистрация настроек, прогрев), обязано быть ленивым или
  фоновым. `AppState::app_host()` (как и `reader()`) собирает runtime при первом
  обращении — уже под экраном загрузки. Окно создаётся скрытым (`visible: false`)
  и показывается командой `show_window` после первой отрисовки интерфейса, а его
  фон выставляется под тему ОС — так белый кадр webview не мелькает. Ещё до
  бундла `index.html` показывает статичный экран загрузки на системных цветах,
  `src/main.ts` заменяет его оболочкой при монтировании; тексты статичного и
  оболочечного экранов совпадают, чтобы смена не читалась как две загрузки.
  Показ скрытого окна на Linux/Wayland требует `tauri >= 2.12` / `tauri-build >= 2.7`
  (tao >= 0.36): в более старых tao системные кнопки окна не работали до configure
  композитора (tauri-apps/tao#1046).
- Tauri-команды, которые вызывают WASM-плагин, собирают runtime или иную
  тяжёлую работу, делать `async`: синхронные команды выполняются на главном
  потоке и морозят интерфейс (образцы — `invoke_plugin_operation`,
  `select_source_library`, `invoke_base_plugin_operation`, `reader_formats`).
- **Любая команда, обращающаяся к общему `Mutex<AppState>`, должна быть
  `async`.** Бутстрап запускает несколько тяжёлых операций параллельно, каждая
  на время WASM-вызова держит мьютекс. Синхронная команда, которая ждёт этот
  мьютекс, блокирует главный поток, и интерфейс перестаёт реагировать на нажатия.

## Фронтенд

- **Приложение кросс-платформенное, свой движок не поставляет.** Tauri использует
  системный webview: на Windows — WebView2 (Chromium), на macOS — WKWebView
  (WebKit), на Linux — WebKitGTK (WebKit). Код интерфейса SHALL работать на всех
  трёх и SHALL NOT опираться на поведение одного движка. Проверять браузерными
  тестами (Chromium) нужно логику, а не отрисовку конкретного движка; поведение,
  которое от движка зависит (тайминги отрисовки растра, шрифты, буфер обмена),
  сверяется в самом приложении, а правки к нему пишутся так, чтобы быть
  нейтральными и безвредными на остальных движках.
- Фронтенд собран на npm workspaces: корень — приложение оболочки, члены —
  `packages/*` (общие пакеты); один lock на весь workspace.
- Дизайн-система — `packages/ui` (`@context/ui`) на основе примитивов Bits UI и
  вариантов `tailwind-variants`; визуальный язык — «Печатный лист»: спокойная
  бумажная основа, единый гротеск во всём интерфейсе (второго шрифта нет),
  сдержанные радиусы, мягкие тени, акцент
  вместо контрастной рамки. Компоненты (Button, Input,
  Textarea, Select, Checkbox, Progress, Card, Badge, Spinner, Menu, MenuItem,
  Dialog) и токены оформления `tokens.css` по стандартной схеме (`--background`,
  `--foreground`, `--primary`, `--muted`, `--border`, `--ring`, `--radius` и
  `-foreground`-пары). Токены идут палитрами: у каждой — светлый и тёмный наборы;
  активную палитру выбирает атрибут `data-palette`, сторону — `data-theme`.
  Палитры — **«Лён»** (тёплая бумага со смолистым зелёным акцентом, по умолчанию),
  **«Индиго»** (холодная нейтраль с глубоким синим акцентом), **«Янтарь»**
  (тёплая контрастная с бирюзовым акцентом) и **«Графит»** (спокойная нейтральная
  с синим акцентом); названия — короткие русские, одного рода и склада; реестр
  палитр — `packages/ui/src/palettes.ts`. Блок `@theme inline` превращает токены
  в утилиты Tailwind v4. Оболочка строит UI только из этих компонентов и токенов.
  Tailwind v4 подключается в приложении, классы пакета попадают в сборку через
  `@source`. Собственные `<style>`-блоки в Svelte-компонентах не используются —
  только Tailwind-классы и токены (иначе dev-сборка ломается на виртуальных
  CSS-модулях Svelte).
- `packages/ui-schema` (`@context/ui-schema`) — контракт декларативного UI: типы
  узлов, интентов, пространств и каталог разрешённых компонентов с валидацией.
- `packages/ui` (`@context/ui`) — дизайн-система: компоненты и токены `tokens.css`,
  а также рендерер деклараций `UiRenderer`, который рисует узлы `ui-schema`
  компонентами системы и рассылает интенты.
- **Выпадающие списки — только компонент `Select` из `@context/ui`** (Bits UI),
  с API `items: { value, label }[]`. Нативные `<select>`/`<option>` в
  областях запрещены: раскрытый список рисует ОС, и он не подчиняется
  токенам.
- **Единообразие интерактивных состояний.** Обводка — один мягкий токен
  `--border` для полей, кнопок, карточек и пунктов списков (`--input` совпадает
  с ним); hover/выбор показываются фоном, а не контрастной рамкой.
- **Списки — единый лист, а не набор рамок.** Строки списка разделяет тонкий
  `--divider`, а не рамка у каждого пункта; наведение и выбор подсвечивают строку
  фоном (`--surface-hover`/`--surface-selected`). Вложенные блоки — врезка
  `--surface-inset`.
- **Всплывающие слои (меню, диалог, список выбора) отделяются по стороне темы.**
  В светлой — мягкой тенью (подложка затемняется); в тёмной затемнять нечего,
  поэтому слой поднимается светлотой **своего для каждой палитры** цвета
  (`--overlay-surface` задан в блоке каждой темы). Тень — только у всплывающих
  слоёв. Контур слоя — **стандартный `--border` темы**, а не отдельный «яркий»
  токен: обводка обязана быть согласована с остальной темой, а не выделяться
  из неё. Отдельная от темы обводка — та же бессистемная заплатка, что и тень
  «по вкусу».
- **Подсветка наведения и выбора — один полупрозрачный тон.** `--surface-hover`
  (тон чернил) и `--surface-selected` (тон акцента) заданы **полупрозрачными** и
  накладываются поверх любой подложки, поэтому отклик одинаково заметен во всех
  палитрах и на любых поверхностях (страница, карточка, всплывающий слой).
  Непрозрачный цвет из палитры для подсветки не берётся: в тёмных наборах он
  почти сливается с фоном, и пункт «не подсвечивается». Токен `--accent` для
  подсветки не используется.
- **Любая правка оформления согласуется со всей темой сразу.** Прежде чем менять
  цвет, обводку или тень, нужно свериться со всеми палитрами (8 наборов в
  `tokens.css`) и общими токенами, а не добавлять частное значение «по месту».
  Частное значение, выбивающееся из системы, — ошибка, даже если локально
  выглядит нормально.
- **Действия над сущностью — контекстное меню `ActionMenu`** из `@context/ui`
  (`items`, `onselect`) с иконкой-триггером, а не набор рядом стоящих кнопок:
  так случайное нажатие и удаление маловероятны, а элементы компактны.
- **Одиночное действие** (если меню избыточно) — общая иконочная кнопка
  `IconButton` из `@context/ui` с действием `add`/`edit`/`delete`; произвольные
  текстовые кнопки с «Удалить»/«Переименовать» не добавляются.
- **Создание сущности** — поле ввода с кнопкой `add` (`IconButton`) или `SearchCreate`
  рядом, без дублирующей текстовой подписи поля.
- **Список сущностей** собирается из общего `EntityList` (`ListRow` + `MetaList`
  + `ActionMenu`), повторяющиеся уведомления об ошибке — из `ErrorToast`, а
  асинхронные операции области — через `createAsyncState` из `@context/ui`.
- **Страница раздела собирается из общего каркаса `PageShell`**: шапка
  (необязательный надзаголовок-`eyebrow`, заголовок, пояснение, главное действие),
  необязательная **полоса управления** (`controls` — поиск и фильтры) и
  содержимое. Раскладку содержимого задаёт сама страница: каркас не навязывает
  «форму слева, список справа». Название раздела рисует шапка приложения, а
  `PageShell` его не дублирует. Поиск — из `Input` с иконкой-лупой (или
  `SearchCreate`, когда нужны и поиск, и создание).
- **Адаптивность делается на уровне страницы, а не пунктов.** Полоса управления
  на узком окне переносит поиск и действия друг под друга. **Список сущностей
  всегда остаётся вертикальным списком**; сеткой карточек может быть только
  главный экран рабочих мест, где карточка — сама сущность (обложки, действия),
  а не строка данных. **Базовый кегль `html` фиксирован (16px): адаптивность —
  это раскладка, ширина колонок и плотность, а не масштабирование всего
  интерфейса вместе с окном.** **Содержимое выровнено по левому краю**, не по
  центру. Точки перелома и предел ширины контента задаются единообразно (токен
  `--content-max-width`), а не подбираются в каждой области.
- **Точки перелома заданы один раз.** Токены `--breakpoint-mobile` (телефон) и
  `--breakpoint-narrow` (узкое окно) в `packages/ui/src/tokens.css` выводятся в
  утилиты Tailwind (`md:`/`lg:`); для кода на JavaScript (`matchMedia`) те же
  значения лежат в `src/shared/breakpoints.ts`. Медиазапрос не может взять
  значение из CSS-переменной, поэтому при смене значения правятся оба места.
- **Телефон — не уменьшенный десктоп.** На ширине до `--breakpoint-mobile` меню
  разделов переезжает в **нижнюю навигацию** (те же разделы и служебные пункты
  иконками с короткими подписями, высота от цели `--touch-target` и безопасной
  зоны снизу), вкладки разделов в верхней панели не рисуются, рабочее место
  занимает всю ширину. Активна ровно одна компоновка меню: разметка не
  дублируется, а доступные имена и метки для тестов не повторяются.
- **Сенсорные цели.** На грубом указателе (`pointer-coarse:`) кнопки и поля
  поднимаются до 44px (`Button`, `Input`, `Select`), поля получают базовый кегль
  16px — так мобильный webview не приближает страницу при фокусе. Взаимодействие
  не зависит от `hover`: нажатие показывается через `:active`.
- **Безопасные зоны экрана** учитываются токенами `--safe-*` (`env(safe-area-inset-*)`):
  нижняя навигация, шапки и футеры панелей добавляют их к своим отступам.
- **Единая шкала слоёв** `--layer-panel` / `--layer-popup` / `--layer-dialog`:
  всплывающая панель на узком окне (`z: var(--layer-popup)` — контекстное меню
  заметки) стоит выше боковой панели (`--layer-panel`), а диалог — выше обоих.
  Слои не подбираются в местах использования.
- **Боковые панели на узком окне закрываются явно.** `SidePanel` перекрывает
  содержимое на узком окне, поэтому при заданном `onClose` показывает кнопку
  закрытия в шапке; автозакрытие при переходе к заметке остаётся.
- **Навигация — вкладки разделов в верхней панели.** Постоянная верхняя панель
  слева содержит название приложения и состояние — имя открытой библиотеки, —
  а справа — вкладки разделов
  (рабочее место, библиотека, заметки) и служебные действия (уведомления, тема,
  настройки). Название приложения — надпись, а не кнопка; название раздела
  дублируется только в панели контекста и в строке состояния не повторяется. На
  телефоне разделы переезжают в нижнюю полосу, а в панели остаются название и
  служебные действия. Под вкладками — панель контекста раздела с заголовком и
  главным действием.
  Кнопки-иконки задаются в `em`/`rem`, а не в
  `px`. Кнопка настроек — «полоски» (меню), как и прежде. У ряда разделов
  нет жёсткой высоты (`px`-высота запрещена): высота складывается из
  масштабируемых отступов и содержимого.
- **Кнопка темы в шапке переключает только светлую и тёмную.** Третьего
  положения «как в системе» у неё нет: режим следования теме ОС выбирается
  настройкой «Тема оформления» в общих настройках приложения (поле остаётся,
  потому что иначе вернуть системный режим было бы нечем). Если в настройках
  стоит «как в системе», кнопка показывает фактически показанную сторону (иконка
  солнца или луны по теме ОС), а нажатие ставит **противоположную** ей явную
  сторону и сохраняет выбор в настройках. Цикл из трёх положений ломал простое
  переключение: приходилось нажимать дважды, чтобы вернуться к прежней стороне.
  Противоположная сторона считается в дизайн-системе (`oppositeTheme`), а не
  сравнением подписей: подпись нужна только для подсказки кнопки.
- **Полноэкранные настройки — своя шапка на все страницы.** Заголовок текущей
  страницы настроек и кнопка закрытия живут в шапке оболочки (`settings-header`),
  а не в отдельной странице: закрытие доступно с любого пункта меню настроек, а
  не только с «Общих».
- **Один экран информации о файлах приложения.** Страница «Информация» —
  **единственное расположение**: каталог состояния приложения, где лежат
  настройки, плагины, кеш и данные интерфейса. Деления плагинов на «каркас»,
  «приложение», «служебные», «в поставке» и отдельных путей кеша/интерфейса в
  интерфейсе нет: есть просто каталог состояния, а техническое различие —
  внутреннее. Обложки в списке рабочих мест берутся **из самого файла книги или
  её папки** (команда ядра `reader_cover` и батч `workspace_covers`): у
  generic-источника — встроенная в
  EPUB/FB2, у Calibre — соседний файл `cover.*`; поэтому список работает без
  открытой библиотеки. Результат извлечения кладётся в **дисковый кэш обложек**
  ядра (`app-state/cover-cache.json`, ключ — путь, свежесть — размер и время
  изменения файла), поэтому книга разбирается один раз, а не при каждом показе.
  Обложки всех книг рабочих мест готовятся **на бутстрапе** одним вызовом
  `workspace_covers` и кладутся в кэш оболочки (`src/features/library/covers.ts`)
  до первого рендера: список рисуется с обложками сразу, без дорисовки по одной.
  В PDF/DjVu без встроенной обложки её нет, и показывается заглушка.
- **Единый вид пункта списка — `ListRow`** из `@context/ui`: название акцентом
  сверху, метаинформация строкой под ним (общий `MetaList`), действия — контекстным
  меню `ActionMenu` в конце строки. **Без обводки и тени:** наведение и выбор
  подсвечивают всю строку целиком **фоном** (как в списках библиотек и наборов),
  а не рамкой и не «внутренней» подсветкой со скруглёнными краями. **Метаинформация
  начинается с даты** и подаётся
  иконкой (`Icon`) с подсказкой; подпись — только когда дат/однотипных значений
  несколько. Метка провайдера и число заметок — справа от названия (слот
  `trailing`). Отдельные кнопки действий сбоку от пункта не добавляются.
- **Даты — единообразно и по языку интерфейса:** русский — `ДД.ММ.ГГГГ чч:мм`,
  английский — `ММ/ДД/ГГГГ чч:мм AM`. Формат берётся через общий
  `src/shared/format.ts` (`formatDateTime`), а не через локаль окружения:
  системная локаль на чужом языке давала бы чужой порядок частей.
- **Тексты интерфейса — только из словарей `@context/i18n`.** Компоненты и
  модули вызывают `t('ключ')`, а не пишут строку по месту; ключ задаёт русский
  словарь (`dict/ru.ts`), остальные языки обязаны покрыть тот же набор, иначе
  сборка типов не пройдёт. Подстановки — `{name}`, множественные формы —
  объект `one`/`few`/`many`/`other` и склонение по правилам языка
  (`pluralForm`). Язык выбирается настройкой `appearance.language`
  (`app.general`), читается на бутстрапе и применяется к документу
  (`lang`, `data-locale`); смена настройки переводит интерфейс без перезапуска
  по событию `settings:changed`. Декларации настроек ядра и плагинов
  передают заголовки и пояснения **ключами словаря** — хост переводит их
  (`localize`), а произвольный текст оставляет как есть. Имя приложения — тоже
  текст интерфейса: «Контекст» по-русски и «Context» по-английски; оно
  ставится в заголовок окна (`app_title_set`), в `<title>` документа и в
  сведения о приложении, а знак на плашке — буква «К» — не переводится.
- **Поиск визуально распознаётся иконкой** (лупа) внутри общего поля (`Input`
  с иконкой через `SearchCreate`).
- **Навигация между экранами — иконочная кнопка с подсказкой**, а не кликабельный
  текст: возврат к списку рабочих мест — стрелка `К списку рабочих мест`. Имя
  открытой сущности показывается в шапке, а не в панели действий.
- **Текущее рабочее место — только явный выбор пользователя.** Скрытого
  «активного» места нет: при запуске показывается список рабочих мест, место
  становится текущим при открытии/создании/выборе при открытии книги, а при
  удалении текущего места соседнее не выбирается. Реестр хранит
  `currentWorkspaceId` (в файле — совместимое поле `active_workspace_id`), но
  `normalizeRegistry` его не восстанавливает.
- **Открытие книги из библиотеки предлагает выбор рабочего места** — модальный
  `Dialog` (Bits UI) со списком, поиском по имени и созданием нового места. Внутри
  уже открытого места книга («Добавить книгу в «…»») идёт в текущее место без
  диалога. Модальные окна собираются из компонента `Dialog` дизайн-системы, а не
  самодельных overlay. Кнопка добавления книги на странице книги называет целевое
  рабочее место: «Добавить в «<имя>»», при отсутствии открытого места — «Добавить в
  рабочее место» (затем выбор места).
- SDK для UI-плагинов — `src-wasm-sdk/ui-sdk` (типизированные конструкторы
  узлов, пространств и действий), член workspace `src-wasm-sdk/`.
- `packages/testing` (`@context/testing`) — мок моста Tauri (`invoke`,
  `dialog.open`, `listen` с фикстурами); `src/lib/app-bridge.ts` переключает
  реальный Tauri и мок по `VITE_MOCK_BRIDGE=1`.
- Тесты: компонентные — Vitest + `@testing-library/svelte` (`npm test`),
  браузерные — Playwright (`npm run test:e2e`: мок-мост, визуальная регрессия).
- **Одна функциональность — один компонент, переиспользуемый везде.** Если
  поведение или элемент интерфейса нужны в двух местах (например, контекстное
  меню заметки и в текучем чтении, и в страничном плагине), выносим их в
  общий компонент/модуль и переиспользуем. Нельзя делать «то же самое»
  разными реализациями в разных местах — это порождает расхождения в виде,
  поведении и постоянные переделки. Плагин формата чтения не рисует
  собственную копию интерфейса заметок: меню и правка заметок принадлежат
  оболочке и передаются в плагин сообщениями.
- **Инструменты заметок видны всегда, пока открыта книга.** Панель чтения
  (`NoteToolbar`) показывает типы, вид фигуры и палитру цветов независимо от
  того, открыта ли панель заметок: заметка создаётся выделением на странице, а
  панель заметок лишь ведёт список. Скрывать инструменты вместе с панелью —
  значит прятать от пользователя саму возможность делать заметки. Подсказка
  кнопки типа объясняет назначение («Выделить текст на странице и сохранить
  цитату»), а не повторяет её подпись.
- **Найденное поиском — рабочий слой, а не заметка.** Поиск по содержимому книги
  открывается кнопкой в панели чтения и панелью поверх области содержимого;
  поиск выполняет та сторона, которая владеет текстом (встроенное чтение — по
  главам, плагин формата — по текстовому слою страниц), а оболочка получает
  только счётчик и номер вхождения. Найденное подсвечивается своим тоном
  (`--rt-search` в теме области чтения) и своим классом, заметки при поиске не
  перерисовываются, а закрытие поиска снимает подсветку без следа. Плагин
  формата не рисует собственную панель поиска: панель — оболочки, команды
  `search`/`search-step` и ответ `search` идут по протоколу рабочего места.
- **Числовые элементы панели не «прыгают».** Номер страницы, прогресс и масштаб
  имеют фиксированную ширину (`w-[…rem]`) и стоят отдельными блоками, поэтому
  смена числа цифр (9 → 10 → 100) не перестраивает панель.
- **Комбинации клавиш — только через общий реестр.** Клавиши приложения живут в
  `src/features/hotkeys/`: каталог действий (`actions.ts`), реестр привязок с
  проверкой конфликтов (`registry.ts`), единый диспетчер с одним слушателем
  `keydown` (`dispatcher.ts`) и стек закрываемых слоёв (`dismiss-layer.ts`).
  Одно сочетание не может быть назначено двум действиям: конфликт — ошибка при
  сборке реестра, а не поведение «кто первый подписался». Собственный
  `keydown`/`svelte:window onkeydown` в компонентах областей не заводится —
  область регистрирует обработчики своих действий в диспетчере и этим объявляет
  их доступность. Клавиша описывается **физическим кодом** (`event.code`), а не
  символом: при русской раскладке `Ctrl+F` должен работать так же, как при
  английской. Комбинации без модификатора не срабатывают в полях ввода и не
  отбирают прокрутку у списков; `Escape` закрывает последний открытый слой
  (настройки, поиск, меню заметки, правку), а не каждый слой по-своему.
- **Книга не трактует клавиши по месту.** Встроенное чтение пересылает нажатие
  общему диспетчеру, плагин формата получает описания привязок сообщением
  `hotkey-bindings`, распознаёт нажатие и сообщает действие `hotkey`, а
  выполняет его приложение командой `command`. Собственная навигация по
  клавишам в документе книги или в плагине — ошибка: иначе одно сочетание
  означало бы разное в разных форматах.

## Доведение работы до конца

- **Начатая задача доводится до рабочего состояния.** Незаконченная правка — не
  результат; «стало лучше» не считается выполнением.
- **Свои правки не откатываются никогда.** Если правка сломала соседнее
  поведение, устраняется причина поломки, а работа продолжается вперёд. Откат
  недопустим даже при трудностях: он стирает сделанное и возвращает ошибку на
  место.
- **Проверка должна ловить поломку, а не подтверждать работу.** Добавляемый тест
  воспроизводит условия, при которых ошибка проявляется, и падает без
  исправления. Тест, проходящий одинаково до и после правки, ничего не
  подтверждает.
- **Проверяется всё, что могло затронуть изменение, а не только его сценарий.**
  Правка в одном месте не должна останавливать работу соседних экранов.
- **Стоимость работы входит в корректность.** Повторяющаяся работа на отрисовку
  или открытие экрана выполняется один раз или кэшируется, а объём проверок
  берётся реалистичный, а не минимальный.

## Проверки перед завершением задачи

Единая точка входа — `make` (см. `make help`). Артефакты плагинов генерируются
из исходников в `src-wasm-plugins/` и в git не хранятся; команды, которым нужны
плагины, собирают их сами, поэтому отдельно помнить про пересборку не нужно.

```bash
make verify        # полный набор проверок
```

`make verify` последовательно выполняет: сборку плагинов (`plugins`), проверку
актуальности артефактов (`check-artifacts`), тесты Rust ядра и WASM-плагинов
(`cargo test`), `clippy` и `fmt --check` для трёх workspace (ядро
`src-tauri`, плагины `src-wasm-plugins` и SDK `src-wasm-sdk` под
`wasm32-unknown-unknown`), `npm run check`, модульные
тесты, браузерные тесты, полную сборку и `openspec validate --all`. Отдельные
шаги доступны как `make test`, `make e2e`, `make build`, `make rust-check`,
`make check`.

Все проверки должны проходить без ошибок и предупреждений. Сборка плагинов —
только через `make plugins` / `scripts/build-wasm-plugins.sh`; манифесты плагинов
лежат в исходниках (`src-wasm-plugins/<name>/plugin-manifest.json`) и не
дублируются в скрипте.

**Завершение работы — уборка за собой.** После проверок не оставлять запущенных
процессов и временных файлов: dev-сервер (`npm run dev:test`, `vite` на 1420),
браузерные прогоны (`playwright`, `chromium`) и всё, что было запущено в фоне,
останавливать до конца задачи; временные снимки, спек-файлы и `test-results/`
удалять. Пользователь не должен сообщать об этом отдельно.

## Общение

- Отвечать пользователю кратко и по делу на русском языке.
- Коммитить только по явному запросу.
- **Делать ровно то, что попросили, и не больше.** Если дан конкретный пример
  результата — воспроизводить именно его, буквально, без «улучшений», без
  возврата вырезанных частей и без соседних правок. Не додумывать за
