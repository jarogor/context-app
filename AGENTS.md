# AGENTS.md — правила разработки «Контекста»

Коротко и по делу: правила, которые нельзя вывести из кода. Тяжёлые объяснения
и история решений живут в `CONCEPT.md` (устройство), `ROADMAP.md` (направление) и
`README.md` (запуск).

## Процесс

- Работать только внутри рабочей директории проекта. Временное — в `_tmp/`
  (в git не попадает).
- Не искать и не обходить файловую систему за пределами проекта (никаких
  `find /`, `find ~`, `/usr`, `/opt`). Нужного исходника вне проекта — нет;
  ответ берётся из кода, документации или lock-файлов.
- Перед правкой кратко изложить план. Перед удалением файлов и директорий —
  спросить. `.env` без явного согласия не менять.
- Делать ровно то, что попросили: без «улучшений» и соседних правок. При
  неясности — спросить.
- **Начатую задачу доводить до рабочего состояния.** «Стало лучше» — не
  результат.
- **Свои правки не откатывать.** Сломалось соседнее поведение — исправлять
  причину и идти вперёд.
- **Историю git не переписывать:** никаких `reset`, `revert`, `--amend` и
  удаления коммитов. Коммит — только по явному запросу, сообщение — одно
  предложение по делу. Ошибка исправляется новым коммитом вперёд.
- После работы не оставлять процессов (vite, playwright, chromium) и временных
  файлов (`test-results/`, снимки, черновики).

## Общение

Русский язык, кратко и по существу. О проблеме говорить прямо; не обещать
обратного сделанному.

## Концепция и планирование

- `CONCEPT.md` — целевое устройство и инварианты. Направление не должно с ним
  расходиться.
- `ROADMAP.md` — приоритеты и этапы. Перед выбором задачи свериться с ним и с
  фактическим кодом: состояние кода важнее статусов в таблице.
- Весь код проекта пишет ИИ-агент. Ошибка в коде — ошибка агента, независимо от
  того, когда она появилась.

## Именование

- Каталоги и файлы приложения — `kebab-case` (`app-state`, `base-plugins`,
  `library-history.json`).
- Ключи внутри JSON-файлов — `snake_case` (`added_at_millis`, `active_tab_id`).
- Идентификаторы плагинов — UUID; папки состояния — по UUID.
- Возможности — `<домен>.<сущность>@<версия>` (`books-source.catalog@1`,
  `settings.store@1`).
- Ключи настроек — точечные сегменты `snake_case` (`appearance.palette`,
  `window.open_tabs_limit`).
- Чужие имена (`WebKitCache`, `hsts-storage.sqlite`) не смешивать с нашими: они
  изолируются в подкаталог (`app-state/webview`).

## Структура кода

Код организуется **вертикальными срезами** по назначению, а не по техническим
слоям: область или плагин держит свои данные, логику и тесты рядом
(`src/features/<область>/`, `src-wasm-plugins/<плагин>/`). Общий код выносится в
`src/shared/`, `packages/*` и `src-wasm-sdk/*` только когда его используют
несколько срезов.

Внутри среза — три слоя, каждый в своих файлах:

1. **Данные** — структуры и DTO без поведения: `models.rs` модуля.
2. **Логика** — функции и методы: `mod.rs` модуля или отдельный файл фичи.
3. **Тесты** — всегда в отдельном файле: `foo.rs` → `foo_tests.rs`; `mod.rs` →
   `_tests.rs` в папке модуля; подключение через
   `#[cfg(test)] #[path = "foo_tests.rs"] mod tests;`.

Новый код писать по образцу соседних модулей.

### Rust

- Не писать однострочных `if`/`for`/`while` без скобок.
- По умолчанию `pub(crate)`; приватные помощники — рядом с местом использования.
- Никаких комментариев-шума и «мёртвого» кода.
- Комментарии и документация — на русском. `///` обязательны для структур,
  полей, перечислений и их вариантов, функций и методов; модуль начинается с
  `//!`. Стиль — дескриптивный: «Получение…», «Создание…».
- Существующие комментарии при редактировании не удалять.
- Комментировать только неочевидное.

### Тесты

- Нативные `Assert`, без FluentAssertions.
- Тест должен **ловить поломку**: воспроизводить условия ошибки и падать без
  исправления. Тест, проходящий одинаково до и после правки, ничего не
  подтверждает.
- Проверять всё, что могло затронуть изменение, а не только его сценарий.
- Тесты повторяют архитектуру: юнит — рядом с модулем, браузерный — в `tests/e2e`.

## Плагины

- **Плагин — самостоятельное приложение.** Он не делит код, тулчейн и
  зависимости с оболочкой и может жить в отдельном репозитории. Связь — только
  через объявленные права и возможности.
- Формат книги обслуживает **свой плагин формата**
  (`src-wasm-plugins/format-<формат>/`, `kind: "format"`), рисующий только
  область содержимого. Встроенного чтения форматов в оболочке нет: ни списка
  форматов, ни парсинга книг. Разбор формата — в плагине или в
  `src-wasm-sdk/format-parsers`, но не в оболочке.
- Источник книг распознаёт корень, сканирует и починяет книги сам; ядро работает
  с общими моделями `source-protocol` и предметного смысла не знает. Совместимость
  с менеджером (Calibre) — отдельный плагин поверх общего.
- Разница между форматами выражается возможностями плагина (`capabilities`), а не
  особой веткой в оболочке.
- Автономные frontend-плагины (`kind: "ui"`, iframe, отдельная сборка) не
  поддерживаются. Интерфейс встроенных областей принадлежит приложению.
- Сетевой источник обновлений — только HTTPS; сетевые пакеты проверяются по
  SHA-256.
- Исходники плагинов — `src-wasm-plugins/` (один плагин — одна папка); SDK
  каркаса — `src-wasm-sdk/`; сборка — `scripts/build-wasm-plugins.sh`, артефакты —
  `src-tauri/resources/plugins/` и `base-plugins/`.
- Журнал диагностики — `plugin::diagnostics` (`app-state/diagnostics.log`);
  отдельной ленты уведомлений в интерфейсе нет.

## Служебные JSON-документы

- У каждого файла есть схема: `schemas/v<версия>/<вид>.schema.json` (JSON Schema
  2020-12), примеры — `schemas/v<версия>/examples/`. Схема — источник истины по
  форме, проверяется в тестах и применяется при чтении и записи.
- Файл опознаётся по метке `format` (`context.<вид>`), а не по месту; у манифеста
  плагина и индекса обновлений метка — имя файла и `contract_version`.
- `version` — версия формата, а не данных. Документ новее известной версии не
  читается. Новое поле требует повышения версии.
- Старая версия читается новой программой: своя схема и шаг `upgrade` к
  следующей. Схемы прежних версий не удаляются, пока читаются прежние документы.
- Проверка обязательна и при чтении, и при записи (`src-tauri/src/documents/`):
  битые данные не попадают на диск.
- Opaque-поля (`properties`, `annotations`, декларации настроек) схемой не
  описываются — ядро их не интерпретирует.
- Схема состояния плагина принадлежит плагину; манифест и индекс обновлений —
  ядру.

## Ядро и запуск

- **Бутстрап — единственное место для загрузки.** `Root.svelte` держит фазы
  `boot → ready | error`, `App.svelte` монтируется только в `ready`, состояние
  грузит `src/features/lifecycle/bootstrap.ts`. Всё, что нужно области при первом
  открытии, читается до первого кадра и передаётся пропом: ленивая загрузка даёт
  подвисание и неполный кадр.
- Тяжёлая инициализация не задерживает появление окна: `setup` не грузит WASM.
  Окно создаётся скрытым и показывается после первой отрисовки; до бундла
  `index.html` показывает статичный экран загрузки.
- **Любая команда с `Mutex<AppState>`, вызовом WASM или иной тяжёлой работой —
  `async`.** Синхронная команда блокирует главный поток и морозит интерфейс.

## Интерфейс

- Только `@context/ui`: компоненты и токены `tokens.css`. Собственных `<style>`
  в Svelte нет — только Tailwind-классы и токены.
- Одна функциональность — один компонент, переиспользуемый везде. Плагин формата
  не рисует свою копию меню заметок или поиска.
- Действия над сущностью — контекстное меню `ActionMenu`; одиночное действие —
  `IconButton`. Списки — `EntityList`/`ListRow`, страницы — `PageShell`,
  уведомления — `ErrorToast`, асинхронные операции — `createAsyncState`.
- Всплывающие списки — `Select` из `@context/ui`; нативных `<select>` нет.
- Оформление согласуется со всей темой сразу (все палитры): частные цвета,
  обводки и тени «по месту» — ошибка.
- **Ничего не сдвигает основание того, на что нажимают.** Полосы вкладок, кнопки
  и переключатели не переезжают от появления соседнего блока. Вкладки стоят над
  поиском и держат место всегда. Проверяется тестом.
- **Адаптивность — это раскладка, а не масштаб.** Базовый кегль `html` — 16px;
  содержимое выровнено по левому краю; предел ширины контента — токен.
- **Точки перелома заданы один раз.** Токены `--breakpoint-phone`, `-tablet`,
  `-large-tablet`, `-desktop`, `-large-desktop`, `-huge-desktop` в `tokens.css`
  дают утилиты `phone:`, `tablet:`, `large-tablet:`, `desktop:`… и парные
  `max-large-tablet:`; для `matchMedia` — `src/shared/breakpoints.ts`.
  Стандартные `sm:`/`lg:` и произвольные `min-[…]` не используются.
- **Смена компоновки — по одному порогу** `large-tablet` (1024px): навигация,
  накладные боковые панели, панель чтения внизу. Одна компоновка меню, без
  дублирования разметки и имён для тестов. На телефоне — нижняя навигация.
- Сенсорные цели — от `--touch-target` (`pointer-coarse:`), безопасные зоны —
  `--safe-top`/`--safe-bottom`/`--safe-left`/`--safe-right`, слои —
  `--layer-panel`, `--layer-popup`, `--layer-dialog`; не подбирать по месту.
- Тексты — только из `@context/i18n` (`t('ключ')`, русский словарь задаёт набор);
  даты — через `src/shared/format.ts`, по языку интерфейса.
- Комбинации клавиш — только через `src/features/hotkeys/`: каталог действий,
  реестр без конфликтов, один диспетчер. Клавиша — по `event.code`. Плагин
  формата получает привязки и сообщает действие, а не трактует клавиши сам.
- Свойства открытого файла кэшируются на диске (`app-state/reader-cache/`) и
  показываются сразу при открытии вкладки; разбирает файл только открытая
  вкладка. Данные плагина — opaque.

## Проверки

Единая точка входа — `make` (`make help`). Артефакты плагинов генерируются и в git
не хранятся; команды собирают их сами.

```bash
make verify
```

Сборка плагинов и проверка артефактов, тесты Rust и фронтенда, `clippy` и `fmt`
для трёх workspace, `svelte-check`, браузерные тесты, полная сборка. Все проверки
проходят без ошибок и предупреждений.

Отдельные шаги: `make plugins`, `make test`, `make rust-check`, `make check`,
`make e2e`, `make build`.
