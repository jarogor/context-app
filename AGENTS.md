# AGENTS.md — правила разработки Текстуры

Правила относятся к Rust-коду (`src-tauri/`) и организации проекта. Их нужно
соблюдать при любой правке, чтобы структура оставалась предсказуемой.

## Планирование и дорожная карта

- Источник истины по направлению, доменам и приоритетам — `ROADMAP.md`.
  Перед планированием и выбором задачи сверяться с ним.
- Текущее состояние функциональности фиксируют `openspec/specs/`, конкретные
  задачи — `openspec/changes/<change>/`.
- Смысловые развилки записывать в «Журнал решений» в `ROADMAP.md`, а не только
  в чат.

## Документация

- `_docs/` — **не** официальная документация проекта, а краткая локальная
  техсправка разработчика: как устроено, как делать и как тестировать. Она в
  игноре контроля версий и нужна только для текущего процесса разработки.
- `_docs/` **не источник истины**: опираться на неё не нужно. Источники истины —
  код, `openspec/specs/` и `ROADMAP.md`.
- Если `_docs/` противоречит сложившемуся состоянию, её нужно исправлять, а не
  следовать ей.

## Разделение кода по файлам

Код делится на три слоя, и каждый слой живёт в своих файлах:

1. **Структуры и DTO** — только данные, без поведенческой логики:
   - доменные сущности каталога — `catalog/entities/<сущность>.rs`, по одной
     структуре на файл, с переэкспортом из `catalog/entities/mod.rs`;
   - прочие DTO модуля — в `models.rs` рядом с логикой модуля (например,
     `sources/models.rs`, `config/models.rs`, `import/models.rs`).
2. **Логика** — функции и методы работы с данными: `mod.rs` модуля или
   отдельный файл фичи (`scanner.rs`, `index.rs`, `repository.rs`, `schema.rs`).
3. **Тесты** — всегда в отдельном файле, никогда inline в исходнике:
   - `foo.rs` → `foo_tests.rs`;
   - координатор модуля `mod.rs` → `_tests.rs` в папке модуля;
   - подключение через:
     ```rust
     #[cfg(test)]
     #[path = "foo_tests.rs"]
     mod tests;
     ```

Новый код пишем по образцу соседних модулей: `catalog/entities/`,
`import/epub_parser/models.rs`, `plugin/plugin_manifest.rs` + `*_tests.rs`.

## Комментарии

- Все комментарии и документация — на русском языке.
- Doc-комментарии (`///`) обязательны для:
  - каждой структуры и перечисления (и каждого варианта перечисления);
  - каждого поля структуры;
  - каждого метода и функции.
- Модуль начинается с `//!`-описания назначения.
- Комментарии к методу пишутся в дескриптивном стиле («Создание/Обновление/
  Удаление», «Получение…»), а не в императивном.
- Отдельные комментарии — только для неочевидной логики; не комментируй
  очевидное.
- Существующие комментарии при редактировании не удалять.

## Общие конвенции Rust

- Не использовать однострочные `if`/`for`/`while` без блочных скобок.
- Не добавлять комментарии-шум и «мёртвый» код.
- Приватные вспомогательные функции размещать рядом с местом использования.
- Публичные API минимальны: по умолчанию `pub(crate)`.

## Плагинная архитектура

- Функциональность, специфичная для формата каталога, реализуется только
  плагинами (`plugin/`): сторонние библиотеки читаются source-плагинами
  (`kind: "source"`) через host-функции `fs_list_dir`/`fs_read_text`, а ядро
  оперирует общими моделями из `sources/` (`ExternalBook`, локальный индекс).
- Ядро `library/` не знает о конкретных источниках: распознавание корня
  (`probe`), сканирование (`scan`) и починку (`scan_book`) выполняет
  выбранный source-плагин.
- Исходники WASM-плагинов живут в workspace `src-wasm-plugins/` (один плагин —
  одна подпапка); сборка всех плагинов — `scripts/build-wasm-plugins.sh`,
  поставляемые артефакты — в `src-tauri/resources/plugins/`.
- Базовый плагин создания/открытия библиотеки живёт в `src-wasm-plugins/library/`
  и поставляется в `src-tauri/resources/plugins/library/`.
- Каркас приложения держит базовые плагины отдельно от session-плагинов:
  app-level `AppPluginHost` грузит плагины категории `kind: "base"` из
  `src-tauri/resources/base-plugins/`, а per-library `PluginSession` — source и
  extension-плагины из `resources/plugins/` и `plugins/` библиотеки.
- Host-функции `log`/`notify` только публикуют событие в `plugin::bus`; его
  доставляет app-level runtime плагину, предоставляющему capability
  `notifications.journal@1`. Ядро не хранит журнал и не интерпретирует его модель.
- Host-функция `emit_event(name, payload)` — generic relay прикладных событий
  Tauri; базовые plugins используют её для live-обновления встроенных
  поверхностей приложения.
- Автономные frontend-плагины (`kind: "ui"`, iframe, отдельные сборки) не
  поддерживаются: ядро и оболочка не загружают их. Интерфейс встроенных
  поверхностей принадлежит приложению и собирается из `@texture/ui`.
- Базовый плагин уведомлений — `src-wasm-plugins/notifications/`; UI журнала —
  встроенная поверхность оболочки `src/lib/NotificationsPanel.svelte`.
- Базовый плагин настроек — `src-wasm-plugins/settings/`; предоставляет capability
  `settings.store@1` и владеет реестром секций и значений настроек в служебном
  состоянии. Плагин объявляет секции настроек в необязательном поле `settings`
  своего манифеста; секция описывает поля с человекочитаемым названием, типом
  (`boolean`/`string`/`number`/`select`/`json`) и значением по умолчанию. Ядро
  передаёт декларации как opaque-схему и не интерпретирует их. Ядро собирает
  реестр из базовых, сессионных деклараций и собственной секции приложения и
  регистрирует его через opaque-операцию `register`. Интерфейс секций плагин
  отдаёт декларативным деревом `ui-schema` в пространстве `settings.section`
  (операция `ui`), а взаимодействие принимает интентом `{space, id, action,
  values}` (операция `intent`); поля в дерево превращает SDK `ui-sdk`, а рисует
  его рендерер `@texture/ui`. UI настроек — встроенная поверхность оболочки
  `src/lib/SettingsPage.svelte`, не знающая о типах полей. Примеры:
  `app.general.startup.welcome_notification` (читает ядро) и
  `notifications.notifications.technical_visible_default` (читает поверхность
  уведомлений).

## Старт приложения и загрузка

- В приложении есть **стадия начальной загрузки (бутстрап)**: `Root.svelte`
  держит фазы `boot → ready | error`, оболочка `App.svelte` монтируется только
  в фазе `ready`, а состояние грузит чистый модуль `src/lib/bootstrap.ts`
  (`loadBootstrap`).
- **Всё, что требует загрузки, выполнять на бутстрапе, а не лениво в процессе
  эксплуатации.** Данные, которые поверхность иначе запросила бы при первом
  открытии (декларации настроек, журнал, каталог стора и т.п.), нужно читать до
  первого кадра и передавать поверхности пропом. Ленивая загрузка даёт
  подвисание при первом обращении к разделу и промежуточный неполный кадр.
- Перед первым рендером состояние должно быть полным: пока грузится — экран
  загрузки, при ошибке — отдельное состояние с повтором, но не пустой и не
  частично готовый интерфейс.
- Tauri-команды, которые вызывают WASM-плагин, собирают runtime или иную
  тяжёлую работу, делать `async`: синхронные команды выполняются на главном
  потоке и морозят интерфейс (образцы — `invoke_plugin_operation`,
  `select_source_library`, `invoke_base_plugin_operation`, `reader_formats`).
- **Любая команда, обращающаяся к общему `Mutex<AppState>`, должна быть
  `async`.** Бутстрап запускает несколько тяжёлых операций параллельно, каждая
  на время WASM-вызова держит мьютекс. Синхронная команда, которая ждёт этот
  мьютекс, блокирует главный поток, и интерфейс перестаёт реагировать на нажатия.

## Фронтенд

- Фронтенд собран на npm workspaces: корень — приложение оболочки, члены —
  `packages/*` (общие пакеты); один lock на весь workspace.
- Дизайн-система — `packages/ui` (`@texture/ui`): компоненты (Button, Input,
  Textarea, Select, Checkbox, Card, Badge, Spinner, Menu, MenuItem) и токены
  оформления `tokens.css`. Оболочка строит UI только из этих компонентов и
  токенов. Tailwind v4 подключается в приложении, классы пакета попадают в
  сборку через `@source`. Собственные `<style>`-блоки в Svelte-компонентах не
  используются — только Tailwind-классы и токены (иначе dev-сборка ломается на
  виртуальных CSS-модулях Svelte).
- `packages/ui-schema` (`@texture/ui-schema`) — контракт декларативного UI: типы
  узлов, интентов, пространств и каталог разрешённых компонентов с валидацией.
- `packages/ui` (`@texture/ui`) — дизайн-система: компоненты и токены `tokens.css`,
  а также рендерер деклараций `UiRenderer`, который рисует узлы `ui-schema`
  компонентами системы и рассылает интенты.
- SDK для UI-плагинов — `src-wasm-plugins/ui-sdk` (типизированные конструкторы
  узлов, пространств и действий), член workspace `src-wasm-plugins/`.
- `packages/testing` (`@texture/testing`) — мок моста Tauri (`invoke`,
  `dialog.open`, `listen` с фикстурами); `src/lib/app-bridge.ts` переключает
  реальный Tauri и мок по `VITE_MOCK_BRIDGE=1`.
- Тесты: компонентные — Vitest + `@testing-library/svelte` (`npm test`),
  браузерные — Playwright (`npm run test:e2e`: мок-мост, визуальная регрессия).

## Проверки перед завершением задачи

Единая точка входа — `make` (см. `make help`). Артефакты плагинов генерируются
из исходников в `src-wasm-plugins/` и в git не хранятся; команды, которым нужны
плагины, собирают их сами, поэтому отдельно помнить про пересборку не нужно.

```bash
make verify        # полный набор проверок
```

`make verify` последовательно выполняет: сборку плагинов (`plugins`), проверку
актуальности артефактов (`check-artifacts`), тесты Rust ядра и WASM-плагинов
(`cargo test`), `clippy` и `fmt --check` для обоих крейтов (ядро и
`src-wasm-plugins` под `wasm32-unknown-unknown`), `npm run check`, модульные
тесты, браузерные тесты, полную сборку и `openspec validate --all`. Отдельные
шаги доступны как `make test`, `make e2e`, `make build`, `make rust-check`,
`make check`.

Все проверки должны проходить без ошибок и предупреждений. Сборка плагинов —
только через `make plugins` / `scripts/build-wasm-plugins.sh`; манифесты плагинов
лежат в исходниках (`src-wasm-plugins/<name>/plugin-manifest.json`) и не
дублируются в скрипте.
