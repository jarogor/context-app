## Context

См. proposal.md — Why. Текущий интерфейс частично строят автономные
frontend-плагины: `plugins/*` собираются отдельными Vite-приложениями в
`public/plugins/` и встраиваются iframe-ом через `src/lib/PluginFrame.svelte`;
манифест помечает их `kind: "ui"`. Ядро (`plugin::PluginRuntime`) грузит только
WASM-плагины и о UI-плагинах не знает — их обслуживает фронтенд.

Задел уже есть: `packages/ui-schema` фиксирует дерево `UiNode`/`UiElement`, где
`on: Record<string, string>` отображает событие узла в идентификатор действия. Это
основа для интентов вместо колбеков. `packages/ui` даёт компоненты и токены.

## Goals / Non-Goals

**Goals:**

- Плагин описывает интерфейс, хост его рисует: контроль оформления у ядра.
- Единство интерфейса: только компоненты и токены дизайн-системы.
- Сторонним плагинам — минимум свободы, разрешённое объявляется явно.
- Взаимодействие без реентерантности и проблем конкурентности.
- Версионируемый контракт и SDK, чтобы развивать интерфейс, не ломая плагины.

**Non-Goals:**

- Полная библиотека UI-компонентов сразу: начинаем с минимума по необходимости.
- UI-конструктор/произвольная вёрстка от плагинов.
- Замена доменных WASM-плагинов: source/base/extension остаются.
- Немедленный перенос всех first-party поверхностей в декларативную модель.

## Decisions

### D1. UI декларативен; рендерит хост

Плагин возвращает дерево интерфейса по `ui-schema`; хост рендерит его
компонентами `@texture/ui`. Плагин не задаёт CSS, вёрстку или свои компоненты.
Альтернатива — автономные frontend-плагины — отвергнута: она разрушает единство
дизайна и даёт неограниченную свободу, которая недопустима для сторонних авторов.

### D2. Пространства интерфейса с идентификаторами

Интерфейс разбит на **пространства** (точки расширения) со стабильными
идентификаторами. Хост публикует каталог: какие пространства существуют, какие
элементы и свойства в них разрешены. Плагин вносит узлы только в разрешённое
пространство и только разрешёнными компонентами. Набор пространств начинается с
минимума под актуальные задачи и расширяется по необходимости. Альтернатива
«свободное дерево без ограничений» отвергнута: ломает единообразие и безопасность.

### D3. Интенты вместо колбеков

Событие узла (`on`) содержит идентификатор действия, а не функцию. При
взаимодействии хост отправляет плагину сообщение `{space, action, values}` как
opaque-запрос. Плагин обрабатывает действие, меняет своё состояние и возвращает
обновлённую декларацию (или признак без изменений). Поток унидирекциональный;
вызовы плагина сериализует хост, поэтому нет реентерантности, гонок и
неконтролируемых колбеков. Это и есть ответ на проблему состояния, из-за которой
колбеки признаны неподходящими.

### D4. Состояние принадлежит плагину

Хост — бездоменный рендерер: хранит только последнюю декларацию по пространству и
не исполняет логику плагина. Состояние (данные, выбор, форма) живёт в плагине —
в его служебном хранилище (`state_read`/`state_write`) или в памяти на время
сессии. Хост может держать эфемерное состояние контролов (текст в поле до
отправки), но источник истины — плагин.

### D5. Версионирование и SDK

Схема UI (`UI_SCHEMA_VERSION`) и контракт плагина версионируются. SDK для Rust
(PDK) даёт типизированные конструкторы узлов, пространств и действий, чтобы
плагин не собирал JSON вручную. Неизвестные узлы/компоненты не ломают хост:
пропускаются или отклоняются с диагностикой; несовместимая версия схемы —
управляемая ошибка. Версии — механизм согласованности при развитии интерфейса.

### D6. Автономные frontend-плагины убираются

`kind: "ui"`, iframe-загрузка, `public/plugins/` и отдельная сборка удаляются. UI
первых плагинов (уведомления, настройки, стор, библиотека) переносится в
приложение как обычные компоненты. Доменные WASM-плагины при этом сохраняются:
они по-прежнему сообщают данные и события, но интерфейс для них рисует хост.

### D7. Минимум сначала

Первые пространства и компоненты определяются по реальной необходимости (например,
секция настроек уже декларативна и служит образцом). Расширение каталога
компонентов — отдельные последующие шаги, а не «всё сразу».

## Risks / Trade-offs

- [Ограничение выразительности UI] → Каталог компонентов расширяется по
  необходимости; сначала минимальный набор, затем точечно.
- [Миграция ломает существующий UI] → Перенос first-party поверхностей идёт
  поэтапно, с сохранением поведения; сначала встроенный UI, потом декларативный
  протокол для сторонних плагинов.
- [Неопределённость протокола состояния] → Явно зафиксировать: полная декларация
  заново vs патч; хранение состояния в плагине. Помечено в открытых вопросах.
- [Совместимость версий схемы] → Версия схемы + контракт; неизвестные узлы не
  ломают хост.

## Migration Plan

1. Зафиксировать модель контракта UI и пространства (спеки).
2. Убрать автономные frontend-плагины: перенести UI уведомлений/настроек/стора/
   библиотеки в приложение, удалить `plugins/*`, `PluginFrame`,
   `build-frontend-plugins.sh`.
3. Ввести протокол декларативного UI: рендерер `ui-schema` в оболочке, команды
   интентов, учёт пространств.
4. Определить пространства и минимальный набор компонентов.
5. По мере необходимости переводить first-party поверхности и сторонние плагины
   на декларативную модель.

Откат — возврат к прежней ревизии; внешних плагинов с UI пока нет, данные не
мигрируются.

## Open Questions

- Точный список пространств интерфейса на старте.
- Минимальный набор компонентов и разрешённых свойств.
- Протокол обновления: плагин возвращает полную декларацию заново или патч.
- Где хранится состояние между вызовами: состояние плагина в storage или
  host-удерживаемое; как это соотносится с сессионностью.
- Нужно ли отдавать first-party UI (настройки/стор/уведомления) через тот же
  декларативный рендерер или оставить нативными компонентами приложения.
