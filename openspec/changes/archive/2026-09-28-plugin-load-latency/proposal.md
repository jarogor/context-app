## Why

Первое использование WASM-плагинов упирается в JIT-компиляцию модулей: замеры
показывают ~2.4 c на базовые плагины при старте и ~3.4 c на source-плагины при
первом открытии библиотеки. Это даёт заметную паузу до прогресс-бара индексации.
Компиляция кэшируется wasmtime на диск и повторно не выполняется, но в
разработке после каждой пересборки `.wasm` кэш инвалидируется, и пауза
возвращается. Предкомпиляция модулей в `.cwasm` убрала бы JIT, однако extism
1.30 через публичный API (`WasmInput`, `Wasm::File`/`Data`) загружает только
сырой WASM и не принимает предкомпилированные модули.

## What Changes

- Убрать блокирующую паузу на компиляции WASM в момент первого открытия
  библиотеки: прогревать модули плагинов заранее (при старте приложения) и/или
  использовать явный постоянный кэш компиляции в области данных приложения.
- Исследовать возможность предкомпиляции в `.cwasm`; если extism (или
  поддерживаемый путь) её не предоставляет — зафиксировать причину и выбрать
  прогрев как рабочее решение.
- Обеспечить диагностируемость: при недоступности кэша загрузка продолжается,
  а не отказывает.

## Capabilities

### New Capabilities

- Отсутствуют.

### Modified Capabilities

- `plugin-system`: загрузка плагинов использует постоянный кэш компиляции и не
  блокирует открытие библиотеки первичной компиляцией source-плагинов.

## Impact

- Ядро: `src-tauri/src/plugin/runtime.rs` (настройка кэша wasmtime, прогрев),
  `src-tauri/src/lib.rs` (предварительный прогрев при старте).
- Сборка: возможно, `scripts/build-wasm-plugins.sh` (предкомпиляция — если
  применимо).
- Зависимости: `extism` (проверить наличие API для предкомпилированных модулей
  в актуальной версии).
