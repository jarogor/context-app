## Context

См. `proposal.md` — Why. Состояние, важное для подхода:

- Хранилище `notes-store` (базовый плагин, capability `notes.store@1`) держит
  **все** наборы всех книг в одном `notes.json` (`NotesState.sets`), но наружу
  отдаёт только `list_for_book(book_key)`. Операции над наборами и заметками уже
  есть; модель заметки несёт `title`, `comment`, `quote`, `chapter`, `page`,
  `percent`, `type`, `color`, `updated_at_millis` — достаточно для превью и
  поиска.
- Ключ книги формирует оболочка: `bookKey(path)` (`src/features/notes/notes.ts`),
  сейчас это абсолютный путь вложения вкладки. Плагин ключ не интерпретирует;
  в `dev_data/base-plugins/notes.json` ключи — абсолютные пути.
- Метаданных книги «по пути» в коде нет: каталог библиотеки индексирует
  относительные пути, обратного разрешения «путь → книга» не существует.
- Состояние заметок живёт в `App.svelte`; панель `NotesPanel.svelte`
  презентационна. Событие хранилища `notes:changed` уже слушается оболочкой
  (`notesRevision`) и перечитывает заметки — тот же сигнал подойдёт реестру.
- Встроенные области грузятся **на бутстрапе** (`features/lifecycle/
  bootstrap.ts`) и передаются пропами; ошибка необязательных данных не прерывает
  вход (`AGENTS.md`, спека `app-shell`).
- Разделы приложения — флаги в `App.svelte` (шапка + область в `<main>`), по
  образцу страницы «Библиотеки»; переход к книге из библиотеки идёт через
  `placeBook`/`openBookInWorkspace` и `reader.goto(note)`.

## Goals / Non-Goals

**Goals:**

- Агрегатный доступ к наборам всех книг из существующего хранилища одним запросом.
- Отдельное пространство заметок в интерфейсе: реестр, группировка по книге,
  глобальный поиск, просмотр заметок набора, переход к книге/заметке.
- Задел под будущую умную идентификацию книги: ключ книги остаётся непрозрачным,
  интерпретация «путь = книга» нигде не закладывается.

**Non-Goals:**

- Реализация умной идентификации книги (`book-identity`): контентные хеши, fuzzy,
  миграция существующих ключей.
- Подборки и вкладки наборов; импорт/экспорт и обмен наборами (`notes-io`).
- Связь с каталогом библиотеки и метаданные книги из индекса.
- Редактирование заметок из реестра (правка остаётся в рабочем месте).

## Decisions

### D1. Агрегат — новая операция `notes-store`, а не обход книг

Данные уже глобальны: `NotesState.sets` — все наборы всех книг. Обход известных
книг вызовом `list_for_book` фрагментарен (наборы книг, не открытых в текущей
библиотеке или рабочем месте, не найдутся) и делает N WASM-вызовов. Поэтому
добавляется операция агрегата `list_all_sets`, возвращающая наборы всех книг
(см. дельту `notes-store`).

Альтернатива: клиентский агрегатор поверх `list_for_book` — отклонена как
неполная и дорогая.

### D2. Агрегат отдаёт наборы вместе с заметками; поиск — в оболочке

`list_all_sets` возвращает наборы **с их заметками** (не только сводки). Личных
заметок немного, а состояние плагина и так читается целиком, поэтому отдельная
операция поиска не нужна: правила поиска (по каким полям, локализация) — дело
клиента, а не opaque-хранилища. Оболочка переиспользует существующие
`noteName`/`filterNotes`/`noteList` из `features/notes/notes.ts`.

Альтернатива: операция `search` в плагине — отклонена: преждевременно сужает
контракт и переносит правила UI в хранилище.

### D3. Отображаемое имя книги — необязательное поле набора

Метаданных по пути нет, а связывать пространство заметок с каталогом библиотеки
нежелательно (работало бы лишь для книг каталога и скрепляло бы два пространства).
Поэтому набор получает необязательное поле `book_title`, которое оболочка задаёт
при создании набора из человекочитаемого имени открытой книги (у вкладки есть
`title`: имя из библиотеки либо имя файла). Поле непрозрачно для хранилища.

Для существующих наборов без `book_title` реестр показывает **резервное имя**,
выведенное из ключа (имя файла без расширения) — в оболочке, а не в хранилище:
хранилище имя из ключа не выводит.

Альтернатива: разрешать путь через индекс библиотеки — отклонена (связывает
пространства, работает лишь для каталога).

### D4. Задел под умную идентификацию книги (не реализация)

Пользователь отметил, что ключ-путь хрупок: сегодня `~/Downloads/book.pdf` — одна
книга, завтра другая, а заметки «съедут». Устойчивой идентификации пока нет, но
проектируем так, чтобы она подключалась без ломки:

- Ключ книги остаётся **непрозрачным**: ни плагин, ни реестр не разбирают его как
  путь и не предполагают `book_key === path`.
- **Единственная точка формирования ключа** — `bookKey()` в оболочке. Смена
  источника ключа на устойчивый идентификатор (хеш/метаданные) не потребует
  правки ни хранилища, ни реестра.
- Отображаемые данные книги денормализованы в наборе (`book_title`) — набор
  останется опознаваемым, пока идёт будущая перепривязка ключей.

Осознанно **не** делаем: контентные хеши, сравнение по размеру/mtime, миграцию
существующих ключей — это отдельный change `book-identity`.

### D5. Раздел «Заметки» по образцу «Библиотек»; данные — на бутстрапе

Раздел — флаг `notesLibraryOpen`, кнопка-иконка в шапке (между библиотеками и
настройками) и область в `<main>`. Реестр читается на стадии начальной
загрузки: `BootstrapState.notes` = `listAllSets()`; ошибка даёт пустое состояние с
диагностикой и не прерывает вход. Перечитывание — по уже слушаемому событию
`notes:changed`.

Альтернатива: ленивая загрузка при открытии раздела — отклонена правилом
«всё, что требует загрузки, — на бутстрапе» (`AGENTS.md`).

### D6. Переход к книге и заметке — отложенная цель

Действие перехода открывает книгу набора в рабочем месте (через существующий
`placeBook`/диалог выбора места), делает выбранный набор активным (`setActiveSet`)
и просит читалку перейти к заметке (`reader.goto`). Читалка появляется
асинхронно, поэтому переход сохраняет **отложенную цель** (`book_key`, `set_id`,
`note_id`), которую потребляет эффект, когда активная вкладка встанет на нужный
ключ. Недоступная книга обрабатывается как в рабочем месте (сообщение, без
аварии).

### D7. Состояние — в оболочке, область презентационна

Как и для заметок: `App.svelte` держит реестр и навигацию, а область
`NotesLibraryPage.svelte` рисует список, поиск и заметки набора и отдаёт интенты
обработчиками. **Заметки — первичны, книга — подпись:** имя набора — основной
акцент, а имя книги — компактный контекст рядом; заметки набора **свёрнуты** и
раскрываются по клику, поэтому список читается как перечень наборов. Логика
группировки, поиска и отображения переиспользуется из `features/notes/notes.ts`;
общие элементы заметки не дублируются — правило «одна функциональность — один
компонент» (`AGENTS.md`).

## Risks / Trade-offs

- [Разные книги с одним путём сливают заметки] → До `book-identity` не решается;
  изоляция — единственная точка формирования ключа и непрозрачность ключа в
  хранилище/реестре; отдельный change `book-identity`. Риск зафиксирован, не
  маскируется.
- [Агрегат читает все заметки — рост объёма] → Личных заметок немного, состояние
  плагина и так грузится целиком; при росте — SQLite за тем же opaque-контрактом
  (`ROADMAP.md`).
- [Отображаемое имя книги устаревает при переименовании] → Денормализация
  допускает устаревание; будущие `book-identity`/запись книги это решат.
- [Гонка перехода к заметке: читалка ещё не готова] → Отложенная цель,
  потребляемая эффектом по появлению нужной вкладки (D6).
- [Верхняя панель перегружается кнопками] → Новых разделов немного; кнопки
  иконочные и с активным состоянием, порядок фиксирован спекой.

## Migration Plan

Миграции данных нет: `book_title` — необязательное поле с значением по умолчанию,
старые наборы читаются без ошибок и получают резервное имя в реестре. Версия
состояния не поднимается (поле аддитивно, прежние клиенты игнорируют неизвестное).

Порядок: расширить `notes-store` (`list_all_sets`, `book_title`, тесты) → клиент
`notes.ts` (`listAllSets`, передача имени книги, агрегатные типы) → срез
`features/notes-library/` (область + клиент + тесты) → раздел и переход в
`App.svelte` → загрузка на бутстрапе → мок-мост и e2e → документация. Откат —
возврат ветки; данные в хранилище не теряются (аддитивное поле).

## Open Questions

- Форма устойчивого идентификатора книги (хеш содержимого, метаданные, fuzzy) —
  решается в `book-identity`; реестр к этому готов (D4).
- Хранить отображаемое имя книги на наборе или отдельной записью книги — можно
  пересмотреть при `book-identity`, не меняя наблюдаемое поведение реестра.
