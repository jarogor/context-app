## Context

Модуль рисования плагина `workplace-pdf` — единственный файл
`src-wasm-plugins/workplace-pdf/viewer/index.html` (2823 строки): вёрстка,
оформление и ~2400 строк JS одним `<script type="module">`. Мотивация — в
`proposal.md`; здесь — состояние и ограничения, задающие подход.

- **Запуск.** Приложение читает HTML модуля (`reader_viewer`), внедряет в него
  прелюдию с base64-файлами модуля и кладёт результат в песочницу iframe
  `sandbox="allow-scripts"` как `srcdoc` (`src/features/reader/WorkplaceContent.svelte`,
  `viewer-bundle.ts`). Относительные пути внутри `srcdoc` не разрешаются: blob-адрес
  файла даёт только `textureViewerUrl('./файл')` из прелюдии.
- **Обмен.** postMessage по каналу `texture-workplace`; хостовая сторона и типы
  сообщений описаны в `src/features/reader/workplace-protocol.ts`.
- **Развёртывание.** Манифест `viewer: "viewer/index.html"`; внешние ассеты в
  `bundle-assets.json` (pdf.js → `viewer/pdf.mjs`, `viewer/pdf.worker.mjs`);
  `scripts/plugin-artifacts.mjs` копирует каталог плагина целиком в ресурсы,
  файлы `.mjs`/`.js` получают MIME `text/javascript`.
- **Архитектурный принцип** (AGENTS.md): плагин — самостоятельное приложение,
  его исходники, тулчейн и зависимости не общие с оболочкой; плагин должен
  допускать вынос в отдельный репозиторий.
- **Поведение** зафиксировано спеками `reader-pdf`, `reader`,
  `workplace-content-plugins` и браузерным `tests/e2e/pdf-reader.spec.ts`; эти
  контракты — мера корректности переписывания.

## Goals / Non-Goals

**Goals:**

- Разбить полотно на типизированные модули TypeScript по ответственностям.
- Покрыть чистую логику юнит-тестами, выполняемыми в изоляции плагина.
- Собирать модуль рисования самостоятельно (фронтенд-проект плагина) в
  статический `viewer/`, не храня сборку в git.
- Сохранить наблюдаемое поведение читалки 1:1 и не менять контракт плагина.

**Non-Goals:**

- Не менять сообщения/контракт, манифест и `bundle-assets.json`, ядро
  (`reader.rs`, `viewer.rs`, `app_state.rs`) и хостовую сторону оболочки.
- Не улучшать и не менять поведение читалки (никаких «заодно поправлю»).
- Не переводить `workplace-demo` и не вводить общий модуль рисования форматов.
- Не выносить плагин в отдельный репозиторий сейчас, но не мешать этому.

## Decisions

**D1. Исходники viewer — самостоятельный фронтенд-проект внутри каталога
плагина** (`src-wasm-plugins/workplace-pdf/frontend/`), со своим
`package.json`, `tsconfig.json`, `vite.config.ts`, `index.html`-шаблоном и
модулями `src/`. Альтернативы отклонены: исходники в дереве приложения
(`src/features/…`) или новым пакетом `packages/*` связывают плагин с тулчейном и
зависимостями оболочки и ломают независимую разработку/установку (см. AGENTS.md).
Логически проект самостоятелен: он не импортирует код, конфиги и пакеты
оболочки; к сборочному конвейеру репозитория он подключён только для сборки и
проверок (npm-workspace + `make` физически размещают зависимости рядом, как для
WASM-плагинов уже делает общий Cargo workspace).

**D2. Сборка — Vite в режиме библиотечного бандла.** Точка входа JS собирается в
один ESM-файл без code-splitting; статический `index.html`-шаблон подключает
бандл через `textureViewerUrl('./viewer.js')` (модульный `import(blobUrl)`), как
сейчас подключается движок. Вывод — `src-wasm-plugins/workplace-pdf/viewer/`
(в git не хранится). Альтернативы: инлайн всего в один HTML (лишний плагин
сборки), `esbuild` напрямую (ручная сборка HTML), относительный `<script src>`
(не работает в `srcdoc`), оставить один файл (суть изменения).

**D3. pdf.js остаётся внешним ассетом.** Viewer не бандлит движок: адреса
`window.__texturePdfEngine`/`__texturePdfWorker` берутся из `textureViewerUrl`, а
модуль грузит движок динамическим `import(/* @vite-ignore */ url)`. Типы движка
даёт `pdfjs-dist` как devDependency фронтенд-проекта. `bundle-assets.json` и
механизм ассетов не меняются.

**D4. Артефакты плагина не включают исходники фронтенд-проекта.** Декларация
сборки плагина (`bundle-assets.json`) получает необязательный список `exclude`
(например `["frontend"]`), который учитывают и `build`, и `check`
`scripts/plugin-artifacts.mjs`. Без ключа поведение прежнее (обратная
совместимость для остальных плагинов). Альтернативы: неявная конвенция
(«подкаталог с `package.json` — исходники») — скрытая магия; отдельный файл
декларации — лишняя сущность.

**D5. Тесты — vitest фронтенд-проекта плагина (jsdom).** Чистую логику выносим в
модули, свободные от DOM/Canvas/pdf.js: масштаб и привязка канваса к пиксельной
сетке, разбор окон отрисовки, нарезка подсветок и полос выделения по строкам,
геометрия фигур и попадание по ним, разбор сообщений протокола, цвета темы и
перекраски, восстановление концов выделения. Моки рендера и Canvas не делаем:
поведение в среде проверяет существующий e2e `tests/e2e/pdf-reader.spec.ts`.

**D6. Сборку viewer выполняет конвейер плагинов.**
`scripts/build-wasm-plugins.sh` запускает сборку фронтенд-проекта плагина до
`plugin-artifacts.mjs build`, поэтому сборку нельзя «забыть». Проверки viewer
(typecheck, юнит-тесты) — командой фронтенд-проекта, подключённой к `make verify`
наравне с прочими.

**D7. Структура модулей — по ответственностям**, по образцу
`src/features/reader/reader/` (мелкие модули + отдельные `*.test.ts`):
протокол/сообщения, состояние и константы, отрисовка страницы и окна канваса,
текстовый слой и совпадение с растром, живое выделение, заметки и их правка,
тема и перекраска страницы, жесты указателя, точка входа. Оформление — отдельный
CSS-исходник; разметка — `index.html`-шаблон.

## Risks / Trade-offs

- [Регрессии при переносе ~2400 строк] → переносить по подсистемам без изменения
  поведения; сетка — `tests/e2e/pdf-reader.spec.ts` плюс новые юнит-тесты; спеки
  поведения не меняются.
- [jsdom не умеет Canvas/pdf.js] → тестируем только чистые модули; средовые
  проверки остаются браузерными.
- [Правка `plugin-artifacts.mjs` влияет на все плагины] → `exclude` необязателен,
  поведение по умолчанию прежнее; `make check-artifacts` остаётся зелёным.
- [Дублирование сборочных зависимостей в плагине] → осознанная цена
  независимости; физически их поставляет npm-workspace.
- [`viewer/` генерируется, а `check-artifacts` требует его наличия] → сборка
  viewer идёт первой в `build-wasm-plugins.sh`, каталог добавлен в `.gitignore`.

## Migration Plan

Порядок: каркас фронтенд-проекта и сборка → перенос логики по подсистемам с
тестами → перевод владения `viewer/index.html` на сборку → `.gitignore`,
`exclude` в `plugin-artifacts.mjs`, подключение к `build-wasm-plugins.sh` и
`make verify` → удаление прежнего полотняного файла. Откат: прежний
`viewer/index.html` остаётся в истории git; при откате возвращаем его и убираем
шаг сборки — манифест и `bundle-assets.json` не менялись.
