## Context

См. `proposal.md` — Why. Сейчас секция настроек декларирует только `defaults` (map ключ→значение), а `settings-ui` показывает секцию как JSON-редактор. Формат декларации задаёт плагин настроек; ядро передаёт схему opaque.

## Goals / Non-Goals

**Goals:**

- Человекочитаемая форма: у каждого поля есть название, тип и значение по умолчанию.
- Обобщённый, но простой набор типов, достаточный для приложения и плагинов.
- Метаданные полей доступны UI через существующие opaque-операции без изменения ядра.

**Non-Goals:**

- Вложенные объекты/массивы как первоклассные типы (кроме escape hatch `json`).
- Валидация значений в ядре; ядро по-прежнему не интерпретирует схему.
- Условная видимость полей и зависимости между ними.

## Decisions

### 1. Формат секции: `fields` вместо `defaults`

Секция декларирует поля:

```json
{
  "id": "notifications",
  "title": "Журнал",
  "description": "Параметры журнала уведомлений",
  "fields": [
    {
      "key": "technical_visible_default",
      "title": "Показывать технические уведомления",
      "type": "boolean",
      "description": "Включать технический уровень при открытии журнала",
      "default": false
    }
  ]
}
```

Поле: обязательные `key`, `title`, `type`; необязательные `description`, `default`, `options` (для `select`, элементы `{ value, title }`). Значения по умолчанию вычисляются из полей. `defaults` удаляется: формат меняется в рамках capability `settings.store@1` (внешних плагинов нет).

Альтернатива — оставить `defaults` и добавить отдельные `labels` — отклонена: два источника правды для одного поля.

### 2. Типы полей и значение по умолчанию

Поддерживаются `boolean`, `string`, `number`, `select`, `json`. Если `default` не задан, берётся значение по типу: `false` / `""` / `0` / первый вариант / `null`. Неизвестный тип трактуется как `json` (безопасный escape hatch).

### 3. Метаданные полей в операциях

`register` и `list` возвращают секции с полем `fields` (метаданные) и `values` (текущие значения). `get`/`set` не меняются. Ядро продолжает проксировать opaque-payload.

### 4. UI: форма вместо JSON

`settings-ui` строит форму: для каждого поля — название, необязательное описание и контрол по типу. Черновики хранятся строками (`Record<sectionId, Record<key, string>>`), при сохранении конвертируются по типу поля: `boolean` → `true/false`, `number` → число, `select`/`string` → строка, `json` → разобранное значение. Кнопка «Сохранить» отправляет значения секции операцией `set`. Ошибка JSON показывается без сохранения.

Альтернатива — авто-сохранение при каждом изменении — отклонена: лишние записи состояния и события; сохранение по кнопке предсказуемее.

## Risks / Trade-offs

- [`json`-поле возвращает часть сырого редактирования] → только для сложных значений, которых пока нет; обычные поля типизированы.
- [Отсутствует сложная валидация значений] → достаточно для текущих типов; при необходимости добавится в плагине настроек.
- [Изменение формата декларации ломает старый `defaults`] → внешних плагинов нет; оба встроенных источника обновляются в этом же изменении.
