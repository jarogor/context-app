## Context

См. `proposal.md` — Why. Текущее состояние, важное для подхода:

- Каталог данных приложения (`app.path().app_data_dir()`, на Linux —
  `~/.local/share/ru.jarogor.texture/`) сейчас смешивает две раскладки. Наши имена
  задаются явно: `app-state` (`constants.rs`), `app-plugins` (там же). Каталоги
  движка (`CacheStorage`, `WebKitCache`, `mediakeys`, `storage`,
  `hsts-storage.sqlite`) создаёт WebKitGTK сам, без нашего участия.
- Каталог данных webview задаётся либо `dataDirectory` в конфиге окна, либо
  `WebviewWindowBuilder::data_directory(..)`. По документации Tauri путь
  `dataDirectory` «relative to the local data directory, followed by the window
  label» и не подвержен `appDirectoriesOverride`; абсолютный путь задаётся только
  билдером. На Linux/wry это значение становится `base_cache_directory` и
  `base_data_directory` у `WebsiteDataManager` (`webkit2gtk/web_context.rs`).
- Windows создаётся из `tauri.conf.json` (`app.windows`), отдельного билдера в
  коде нет, поэтому конфиг окна — единственная точка, куда можно добавить
  `dataDirectory`.
- `AppInfo::build` (`plugin/app_info.rs`) собирает список расположений для
  страницы «Информация»; каталог webview там не публикуется.
- Спека `app-state` уже фиксирует расположение служебного состояния и разбиение
  dev/release.

## Goals / Non-Goals

**Goals:**

- Одна записанная нотация для служебных имён приложения.
- Убрать чужие имена из корня каталога данных, сгруппировав их под явным
  владельцем — подкаталогом `webview` каталога состояния.
- Сделать каталог webview видимым и объяснённым в снимке `AppInfo`.

**Non-Goals:**

- Переименование уже благополучных имён нашего состояния (`app-state`,
  `workspaces.json`, `library-history.json`, `disabled-plugins.json`,
  `wasm-cache*`, `base-plugins/`) — они уже в `kebab-case` и описывают назначение.
- Перенос прежних данных webview (кеш, localStorage, cookies) на новое место —
  это движковые данные, автоматическая миграция не выполняется.
- Изменение имён JSON-файлов базовых плагинов (`settings.json`, `notes.json`,
  `journal.json`) — их задают плагины, ключ без разделителей пути уже закреплён.
- Наведение порядка в нотации, которая выходит за рамки служебного состояния
  (Rust-код, фронтенд) — только фиксация правила, без массовых переименований.

## Decisions

### D1. Правило нотации — в `AGENTS.md`, проверяемое требование — в спеке

Запись в `AGENTS.md` делает правило обязательным при любой правке, а требование в
спеке `app-state` делает его частью поведения и даёт точке входа `make verify`
(через `openspec validate`) опору. Альтернатива — только спека (разработчик её не
видит при правке) или только `AGENTS.md` (нет проверяемого требования) —
отвергнуты: нужны оба.

### D2. Webview-хранилище — подкаталог `app-state/webview`

Технические каталоги движка переименовать нельзя (их имена задаёт WebKitGTK), но
можно задать базовый каталог данных webview. Выбран подкаталог нашего каталога
состояния (`app-state/webview`), потому что: владелец — приложение (движок лишь
исполнитель), срок жизни и развилка dev/release совпадают с прочим служебным
состоянием, каталог уже попадает под `.gitignore` (`dev_data`). Альтернативы:
отдельный каталог рядом с `app-state` в корне данных (добавляет ещё одно имя в
корень и разводит близкие по смыслу данные) и `app-cache` (кеш — лишь часть того,
что там лежит: ещё cookies и локальное хранилище) — отвергнуты.

### D3. Абсолютный путь через билдер окна

`dataDirectory` в конфиге резолвится относительно каталога локальных данных и
добавляет метку окна (`.../main` на Linux), что даёт лишний уровень и зависит от
платформы. Поэтому каталог задаётся абсолютным путём при создании окна, а окно
создаётся через `WebviewWindowBuilder`, а не неявно из конфига: корень известен в
`setup`, где уже вычисляется `app_state_root`. Проверяемая деталь — что webview
принимает заданный каталог: это подтверждается содержанием каталога после запуска.
Если на какой-то платформе путь не применится, поведение деградирует до текущего
(движок кладёт данные рядом) — это допустимо и не ломает приложение.

### D4. `recent-libraries.json` удаляется, а не мигрируется

Файл не читается ни ядром, ни фронтендом (проверено поиском по проекту), это
остаток прежней версии до появления `library-history.json`. Формат записи
(`["путь", ...]`) не совпадает с `library-history.json`. Приложению достаточно
перестать учитывать его в спеке; удаление самого файла в `dev_data` — разовая
локальная уборка, на поведение не влияет.

### D5. `webview` — не часть «наших» имён в требовании о нотации

Требование о нотации формулируется так, что сторонняя нотация допускается только
для данных, чьё имя задано не приложением, и такие данные обязаны быть
изолированы. Это позволяет не подстраивать требование под `CacheStorage` и прочие
имена движка и одновременно делает изоляцию проверяемой: в корне каталога данных
не должно быть смешанных нотаций.

### D6. `dev_data` исключён из наблюдения Vite

В debug-сборке каталог webview лежит внутри рабочей копии проекта
(`dev_data/app-state/webview`). Vite dev-сервер по умолчанию наблюдает за файлами
проекта, поэтому постоянная перезапись кеша WebKitGTK вызывала бесконечные
`page reload` и `hmr update` — приложение висело на экране загрузки и не
открывалось. `dev_data` добавлен в `server.watch.ignored` рядом с `target`.
Альтернатива — держать webview вне проекта, но тогда теряется единая развилка
dev/release и нарушается D2; альтернатива «не задавать data_directory» —
возвращает движковую нотацию в корень каталога данных. Игнор узкий: слежение за
`src/`, `packages/` и прочим кодом сохраняется.

## Risks / Trade-offs

- [Белый кадр / сброс окна] → `WebviewWindowBuilder` уже используется в проекте;
  окно по-прежнему создаётся скрытым и показывается после отрисовки, поэтому
  смена способа создания не должна изменить сценарий показа.
- [Кеш webview внутри проекта ломает dev-сервер] → `dev_data` исключён из
  `server.watch.ignored` в `vite.config.ts` (D6); без игнора Vite бесконечно
  перезагружает страницу.
- [Потеря движковых данных] → Кеш и cookies webview пересоздаются; для инструмента
  чтения это незначимо. Отмечено в proposal как наблюдаемое изменение.
- [`dataDirectory` игнорируется на macOS] → На macOS используется
  `dataStoreIdentifier`; спека формулирует требование через «каталог данных
  webview», а не через конкретный ключ, поэтому расхождение платформ допустимо.
- [Правило без автоматической проверки] → Нотацию не проверить тестом целиком;
  проверяемой остаётся раскладка (каталог webview и состав каталога состояния),
  а нотация держится правилом и ревью.

## Migration Plan

1. Записать правило нотации в `AGENTS.md`.
2. Добавить каталог webview в `constants.rs`/`paths.rs`, создать окно с
   абсолютным `data_directory` в `lib.rs`.
3. Добавить расположение webview в `AppInfo::build` и покрыть тестом.
4. Обновить `tauri.conf.json` (окно создаётся кодом).
5. Разовая уборка `dev_data/app-state`.
6. Проверить `make verify`.

Откат — вернуть создание окна из конфига и убрать запись `webview`: приложение
снова начнёт складывать данные движка в корне каталога данных. Данные, созданные
по новому пути, при откате просто перестают использоваться движком.
