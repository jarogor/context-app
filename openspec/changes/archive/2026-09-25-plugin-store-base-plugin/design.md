## Context

См. `proposal.md` — Why. Состояние, важное для подхода:

- App-level `AppPluginHost` загружает `kind: base` из `resources/base-plugins/`;
  per-library `PluginSession` — source/extension из `resources/plugins/` и папки
  библиотеки. Единицы поставки плагина нет: плагин — это уже распакованная папка.
- `PluginRuntime::load_plugin_dir` регистрирует все host-функции для каждого
  плагина и не ограничивает их списком `host_functions` манифеста.
- `state_read`/`state_write` дают плагину изолированное хранилище; `fs_*`
  ограничены песочным корнем библиотеки; в сети плагинам отказано
  (`disallow_all_hosts`).
- Есть `sha2`, `base64`; zip-декодера в ядре нет (он есть только внутри
  WASM-плагина библиотеки).
- `lib.rs` вычисляет dev-пути через `CARGO_MANIFEST_DIR` (`dev_data/...`) и
  прокидывает storage base-плагинов (`base_storage_root`).
- Frontend-плагины (`settings-ui`, `notifications-ui`) монтируются в iframe через
  `PluginFrame.svelte`, общаются `layout`-сообщениями и вызываются через
  `invoke_base_plugin_operation`.

## Goals / Non-Goals

**Goals:**

- Единица поставки плагина — zip-пакет; установка/удаление выполняются ядром
  безопасно, без доверия к содержимому архива.
- Пользовательский каталог плагинов уровня приложения, общий для всех библиотек.
- Базовый плагин `plugin-store` с capability `plugin-store@1`: файловая
  установка, реестр сторов, контракт поставщика.
- Привилегированные host-функции доступны только объявившим их плагинам.
- UI стора отдельным frontend-плагином; оболочка владеет только слот-регионом.

**Non-Goals:**

- Реальные сетевые запросы, загрузка из сети, сетевой транспорт.
- Подпись пакетов, проверка доверия, доверенные издатели.
- Обновление/понижение версий установленного плагина, откат.
- Горячая перезагрузка после установки без переоткрытия/перезапуска.
- Frontend-ассеты внутри пакета и динамический реестр frontend-плагинов.
- Установка базовых плагинов каркаса через стор.

## Decisions

### 1. Пакет — zip, распаковывает и валидирует ядро

Пакет — zip-архив с `plugin-manifest.json` в корне и модулем, на который
ссылается манифест. Валидацию манифеста, версии контракта и путей, а также
распаковку выполняет ядро (`PluginManifest` уже умеет валидировать). Добавляется
зависимость `zip` в `src-tauri`; `sha2` используется для проверки контрольной
суммы, если она указана.

Защита от zip slip: для каждой записи нормализуется путь и проверяется, что он
относительный и не выходит за каталог установки; абсолютные пути, `..` и
символические ссылки отклоняются. Альтернатива — распаковка внутри плагина —
отклонена: у WASM-плагина нет доступа к ФС, а доверие к нему не выше, чем к ядру.

### 2. Пользовательский каталог плагинов приложения

Вводится константа `USER_PLUGINS_DIR_NAME = "app-plugins"`. В разработке корень —
`<проект>/dev_data/app-plugins`; в проде — каталог данных приложения
(`app.path().app_data_dir()`). Каталог общий для всех библиотек. Сессия
дополняет список директорий загрузки пользовательским каталогом; при совпадении
имён приоритет: библиотека → пользовательский каталог → поставляемые ресурсы.

Установке доступны только `source`, `extension` и `ui`-пакеты. Базовые плагины
каркаса поставляются только приложением и через стор не устанавливаются и не
удаляются. Альтернатива — единый каталог на библиотеку — отклонена: плагин
должен работать во всех библиотеках.

### 3. Привилегированные host-функции стора и их гейтинг

Добавляются host-функции (path-based, чтобы не гонять zip через память WASM):

| Имя               | Аргумент (UTF-8) | Результат         |
| ----------------- | ---------------- | ----------------- |
| `store_inspect`   | путь к zip       | JSON с манифестом |
| `store_install`   | путь к zip       | JSON с манифестом |
| `store_uninstall` | имя плагина      | `"ok"`            |
| `store_installed` | —                | JSON-список       |

Корень пользовательского каталога передаётся runtime отдельным полем
`plugin_store_root` (по аналогии с `storage_root`). В `load_plugin_dir`
привилегированные функции регистрируются **только** если плагин объявил их в
`host_functions`; это закрывает доступ остальным плагинам. `store_uninstall`
отказывает для имён поставляемых/базовых плагинов.

### 4. Базовый плагин `plugin-store` и capability `plugin-store@1`

`src-wasm-plugins/plugin-store/` — базовый плагин (`kind: base`). Операции
(opaque для ядра, вызываются через `invoke_base_plugin_operation`):

- `capabilities` — виды провайдеров и версия контракта;
- `list` — установленные пакеты (`store_installed`);
- `install_file` — `{ path }`: `store_install(path)`;
- `uninstall` — `{ name }`: `store_uninstall(name)`;
- `stores_list` / `stores_add` / `stores_remove` — реестр сторов в состоянии
  плагина (ключ `stores.json`);
- `available` — `{ store_id }`: индекс пакетов провайдера;
- `install_from_store` — `{ store_id, package }`: установка через провайдер.

Контракт поставщика — `plugin-store.provider@1`: стор описывается
`{ id, kind: "file" | "network", title, location }`, индекс пакета —
`{ name, version, kind, description, location, sha256? }`. Файловый провайдер
читает каталог/`store-index.json`; сетевой провайдер — заглушка, возвращает
`{ supported: false }` без сетевых вызовов. Ядро о контракте ничего не знает.

### 5. UI стора отдельным frontend-плагином

`plugins/plugin-store-ui/` строится по образцу `settings-ui` (Svelte + Vite +
`bridge.ts`): точка входа в верхней панели и страница со списком установленных
плагинов, установкой из файла (диалог выбора `.zip`), удалением и списком
сторов (добавление/удаление; сетевые помечены как неподдерживаемые). Плагин
вызывает `invoke_base_plugin_operation('plugin-store', ...)` и подписывается на
`plugin-store:changed`.

Оболочка (`App.svelte`) добавляет слот-регион стора рядом с регионом настроек;
оболочка владеет только состоянием «страница открыта» и переключает панели,
сохраняя состояние основного плагина. `build-frontend-plugins.sh` собирает
`plugin-store-ui`.

### 6. Доступность установленного плагина

Установленный плагин не загружается в уже работающий runtime: `PluginSession`
читает каталоги при конфигурации. После установки UI показывает уведомление о
необходимости переоткрыть библиотеку (или перезапустить приложение). Горячая
перезагрузка — вне scope; при необходимости runtime можно перезагружать позже
без изменения контракта.

## Risks / Trade-offs

- [Zip slip / вредоносные пути] → нормализация и проверка каждой записи, отказ от абсолютных путей, `..` и ссылок; распаковка в отдельный временный каталог с последующим переносом.
- [Zip-бомба или огромный пакет] → лимиты на размер распакованных данных и число записей.
- [Привилегированные функции доступны не только стору] → гейтинг по `host_functions` манифеста; функция выдаётся лишь объявившему её плагину.
- [Отсутствие подписи] → на текущем этапе пакет не проверяется на авторство; зафиксировано в `ROADMAP.md` как будущий этап (подпись, контроль целостности, доверие).
- [Сетевой провайдер не работает] → заглушка честно сообщает о неподдержке; файловый провайдер независим.
- [Приоритет пользовательского плагина над поставляемым] → осознанно: пользователь может переопределить встроенный плагин; базовые плагины защищены от установки/удаления через стор.
- [Установка требует переоткрытия] → приемлемо для MVP; UI явно сообщает об этом.

## Migration Plan

1. Добавить `zip` в `src-tauri`, константу и dev/prod-пути пользовательского каталога; подключить каталог в загрузку сессии и app-host.
2. Ввести host-функции стора, поле `plugin_store_root` и гейтинг по `host_functions`; реализовать безопасную распаковку и удаление.
3. Добавить WASM-плагин `plugin-store` в workspace и `deploy_plugin` в сборочный скрипт (`base`).
4. Добавить frontend-плагин `plugin-store-ui`, регион стора в оболочке и сборку в `build-frontend-plugins.sh`.
5. Обновить `_docs/plugin-contract.md`, `_docs/structure.md`, `_docs/README.md`; добавить заметку о подписи в `ROADMAP.md`.
6. Откат: изменение аддитивно; при необходимости убрать регион стора, базовый плагин и host-функции, вернув прежний состав.

## Open Questions

- Точное расположение пользовательского каталога в проде (`app_data_dir` и его
  подкаталог) — уточняется при упаковке Tauri, на контракт не влияет.
- Формат файлового индекса стора (`store-index.json` vs сканирование `*.zip`) —
  деталь файлового провайдера, может быть уточнена при реализации.
