## Context

Текущее приложение использует ad-hoc логирование через `println!`/`eprintln!` в нескольких модулях (`lib.rs`, `library/mod.rs`, `plugin/runtime.rs`) и разрозненные Tauri-события `library-progress` и `library-catalog-changed`. Нет централизованного механизма для сбора и отображения событий пользователю. Пользовательский поток кода не имеет доступа к контексту выполнения, необходимому для корректного логирования из доменных методов. (См. `proposal.md` — Why.)

## Goals / Non-Goals

**Goals:**
- Единый backend-журнал событий в памяти с двумя уровнями: пользовательский и технический.
- Интеграция существующих точек логирования и событий в этот журнал.
- раздел интерфейса уведомлений: десктоп — сворачиваемая боковая панель слева, мобильный/узкое окно — отдельная страница.
- Кликабельный счётчик непрочитанных пользовательских уведомлений в глобальном меню на мобильном.
- Отсутствие шума: открытие библиотеки без изменений не порождает User-уведомлений; создание и обновление индекса — по одному агрегированному уведомлению.
- Автоматическая пометка записей как прочитанных при просмотре.
- Включение технических логов по тумблеру, без изменения записи.

**Non-Goals:**
- Персистентность журнала между запусками (session-only, in-memory).
- Перенос зависимостей (`log`, `tracing`) на данном этапе.
- Поддержка нескольких библиотек в рамках одной сессии (журнал глобальный для приложения).
- Детализация конкретных событий импорта (импортированные книги, путь файла) — только факт импорта/ошибка.
- Отслеживание пользовательских действий (поиск, открытие книги) в рамках v1.

## Decisions

### 1. Жизненный цикл журнала: session-only, in-memory

**Решение:** журнал живёт только в памяти в рамках одной сессии приложения, при перезапуске очищается.

**Альтернативы:**
- Персистентный журнал в файле (app-data directory) — требовал бы ротации, ограничение размера и работа с путями на мобильной платформе.
- Split: пользовательские уведомления сохраняются, технические — нет.

**Обоснование:** пользователь не просил историю между запусками; session-only снижает сложность и снимает вопросы с мобильного app-data directory. Если потребуется, можно добавить персистентность позже.

### 2. Архитектура журнала и API

**Решение:**
- Новый модуль `src-tauri/src/journal/mod.rs` с типом `Entry`, `Journal` (bounded `VecDeque`), командами `list_journal`, `mark_read`, `clear_journal` и событием `journal:added`.
- Tauri-managed state: `Arc<Mutex<Journal>>` на уровне `lib.rs`.
- Лёгкий глобальный фасад `JournalHandle` (через `OnceLock`), инжектируемый в `Library` и команды, чтобы избежать сигнатурных изменений `Library` и тестируемости без Tauri.

**Альтернативы:**
- Инъекция `JournalHandle` во все конструкторы `Library` — потребовало бы изменения сигнатур всех конструкторов и тестов.
- Использование crate `log` с кастомным `Log`-реализатором — добавило бы зависимость, не оправдано на данном этапе (большая часть логов — ad-hoc).

**Обоснование:** глобальный фасад с no-op в тестах сохраняет тестируемость `Library` без Tauri и позволяет добавить эмиссию без переписывания конструкторов. Чистый Rust без дополнительных зависимостей, минимальные изменения кодовой базы.

### 3. Уровни записей и семантика `level`

**Решение:** поле `level: Level { User, Technical }`. `severity: Severity { Info, Warn, Error }` для пользовательских уведомлений.

**Альтернативы:**
- Использовать `log::Level` из crate `log` — было бы конгруэнтно с тривиальным `Log`, но не добавляет новой зависимости.
- Бинарный тег без семантики ошибок — терял бы возможность различать критические ошибки.

**Обоснование:** двухуровневая модель (User/Technical) соответствует требованиям; `severity` даёт гибкость для пользовательских ошибок (Error) без усложнения API технических логов.

### 4. раздел интерфейса и адаптивность

**Решение:**
- Десктоп (ширина >= 900px): только докнутая боковая панель слева, по умолчанию свёрнута в узкую полосу со счётчиком. Разворачивание помечает записи как прочитанные. Отдельная кнопка и страница уведомлений на десктопе недоступны.
- Мобильный/узкое окно (< 900px): отдельная страница уведомлений с заголовком, счётчиком и лентой; кликабельный счётчик в глобальном меню открывает страницу, возврат идёт на страницу-источник.
- Разграничение на уровне Svelte: компонент панели рендерится только при `>= 900px`, маршрут страницы уведомлений доступен только при `< 900px`.

**Альтернативы:**
- Использовать `tauri-plugin-os` для детектирования платформы — добавляет зависимость и усложняет.
- Чистый CSS для панели и страницы с JS-навигацией — оставляет риск «пустой страницы» при ресайзе; выбран явный флаг `isMobile` через `matchMedia`.

**Обоснование:** CSS breakpoint покрывает нужный набор случаев (mobile native, узкое десктопное окно), а явный флаг `isMobile` в Svelte гарантирует, что уведомления на десктопе показываются только панелью, а на мобильном — только страницей, без тупиковых состояний. `tauri-plugin-os` не требуется.

### 5. Автоматическое чтение при просмотре

**Решение:** при разворачивании панели или открытии страницы все видимые записи помечаются как прочитанные; новые записи, пришедшие во время просмотра, остаются непрочитанными и увеличивают счётчик.

**Альтернативы:**
- Пометка по клику на каждую запись или кнопка «Прочитать все» — лишние клики, сложнее.
- Всегда показывать 0 счётчика пока панель открыта — не даёт обратной связи о новых событиях.

**Обоснование:** простой UX, соответствующий классическому поведению «колокольчика», но без бесконечно растущего счётчика пока пользователь не свернёт/закроет.

### 6. Техническая логика без crate `log`

**Решение:** заменить явные `println!`/`eprintln!` на вызовы `journal.tech(...)` и дренаж `HostSink`. Никаких новых зависимостей.

**Альтернативы:**
- Добавить `log` + собственный `Log`-реализатор, сделать все вызовы `log::debug!`/`log::info!` — потребовало бы пройтись по большому числу мест.
- Использовать `tracing` crate — ещё более тяжёлое изменение.

**Обоснование:** текущий объём логов невелик; локальный `journal.tech!` более прозрачен и даёт полный контроль над форматом и семантикой, без введения «золотой середины» тривиального logger. Меньше магии и зависимостей.

### 7. Нумерация записей и timestamp

**Решение:** `Entry` содержит уникальный инкрементный `id` и `timestamp` для сортировки и идентификации. Инкремент внутри `Journal` — без использования внешних библиотек.

**Альтернативы:**
- Использовать `chrono`/`time` — добавило бы зависимость.
- Использовать `Arc<AtomicU64>` для id — упрощает, но требует аккуратности при снятии блокировки.

**Обоснование:** минимальные зависимости; `AtomicU64` + монотонный счётчик дают уникальные id с минимумом накладных расходов.

### 8. Ограничение размера журнала

**Решение:** ring buffer с максимальным количеством записей (например, 500). При достижении лимита старые записи удаляются из начала.

**Альтернативы:**
- Без лимита — память может расти неограниченно.
- Персистентный файл с ротацией — выходит за рамки session-only.

**Обоснование:** ограничение protects от потенциального флуда при проблемах с логированием; 500 записей достаточно для типичных сценариев.

### 9. Политика уведомлений об индексе (без шума)

**Решение:**
- Попадание в кэш (библиотека не менялась): переиспользование индекса без пересборки, только техническая запись — без User-уведомления.
- Создание индекса впервые: ровно одно User-событие на всю библиотеку.
- Обновление после реальных изменений в процессе работы: одно агрегированное User-событие на пакет изменений.
- Служебные, скрытые и корневые пути (`metadata.db`, `.booklib`, скрытые каталоги) не вызывают переиндексацию и не порождают уведомления.

**Альтернативы:**
- User-событие «Библиотека открыта из кэша» на каждое открытие — создаёт поток однотипных уведомлений без ценности.
- Уведомление на каждую книгу — превращает ленту в мусор при массовых изменениях.

**Обоснование:** пользователь видит только события с реальной ценностью: индекс создан, индекс изменён, импорт. Фоновые переиспользования кэша и служебные шумные пути остаются на техническом уровне.

## Risks / Trade-offs

[Risk: флуд технических логов] → Mitigation: аккуратный выбор точек логирования; ограниченный ring buffer; протестировать громкие точки (например, `get_cover`) — не логировать их.

[Risk: инъекция глобального фасада может скрыть зависимости] → Mitigation: `JournalHandle` публичен, его можно явно передавать; в тестах `JournalHandle::new_noop()`.

[Risk: мобильный app-data directory не writable] → Mitigation: session-only журнал, не требует записи на диск; при необходимости позже добавить локальное хранилище.

[Risk: раздел интерфейса меняет layout App.svelte] → Mitigation: минимальные изменения: добавить тэг `<NotificationsPanel />`, обновить CSS; layout останется гибким.

[Risk: новые события могут быть неочевидны пользователю] → Mitigation: использовать понятные описания, семантику Error/Warn/Info, минимум технических деталей в пользовательском уровне.

[Trade-off: технические логи не видны без переключателя] → Mitigation: переключатель даёт полный контроль; сообщать пользователю в UI, где он находится.

[Trade-off: session-only журнал не сохраняет важные события] → Mitigation: пользовательская активность (открытие библиотеки, импорт, ошибки) по сути важна только в рамках сессии; если потребуется — расширить позже с персистентностью.
