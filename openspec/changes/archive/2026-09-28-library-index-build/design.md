## Context

См. proposal.md — Why. Текущее состояние: оба source-плагина (`library`,
`library-calibre`) создают схему индекса через `CREATE TABLE IF NOT EXISTS` и
хранят только метаданные каталога; обложка не сохраняется, а извлекается операцией
`cover` при каждом запросе UI. `library-ui` после загрузки списка последовательно
запрашивает обложку для каждой книги (`loadCovers`), из-за чего открытие
библиотеки из сотен книг выглядит как повторное сканирование и приводит к
зависанию. Прогресс не публикуется, UI показывает неопределённую «крутилку».

Схема индекса уже отделена от внешней библиотеки (SQL host API, база вне
директории библиотеки) и привязана к провайдеру и каноническому корню.

## Goals / Non-Goals

**Goals:**

- Управлять схемой индекса версионированными миграциями, чтобы добавлять книги
  новые свойства без перестройки и потери данных.
- Включить обложку в индекс, устранив повторное чтение и разбор файлов.
- Показывать детерминированный прогресс построения индекса в процентах.
- Оставить построение индекса одним проходом, без фонового дозаполнения.

**Non-Goals:**

- Фоновое/постепенное наполнение библиотеки и live-обновления карточек.
- Watcher файловой системы (остаётся будущим шагом `library-index-cache`).
- Массовое переписывание потребления: read-view, импорт и portable-режим не
  затрагиваются по существу.
- Оптимизация размера хранения обложек (миниатюры/сжатие) — возможный следующий шаг.

## Decisions

### D1. Миграции схемы, а не «топорный» CREATE

Вводится общий для source-плагинов механизм миграций: упорядоченный список
`Migration { version, sql }`, применяемый по возрастанию к `PRAGMA user_version`.
Каждый плагин владеет своим списком. Новое свойство книги — новая миграция
(`ALTER TABLE … ADD COLUMN`, новая таблица), применяемая без пересоздания и
перестройки. Миграции оборачиваются в транзакцию; при ошибке состояние не
фиксируется, и плагин переходит к полной перестройке. Версия выше поддерживаемой
— перестройка/диагностируемая ошибка.

Альтернативы: (а) оставить `CREATE TABLE IF NOT EXISTS` — нельзя развивать схему;
(б) пересоздавать базу при каждом изменении схемы — теряется собранный индекс и
требуется полный скан; (в) отдельный SQL-host-API «миграций» в ядре — избыточно,
миграции принадлежат плагину. Механизм реализуется как маленький общий crate
workspace `src-wasm-plugins/`, работающий поверх opaque SQL через замыкания, без
привязки к конкретному `Fs`-трейту.

### D2. Обложка хранится в индексе

Обложка сохраняется в отдельной таблице `covers(book_id, format, mtime_ms, data)` в
том же проходе, что и метаданные: `metadata::extract` уже возвращает байты обложки
при чтении файла, сейчас они выбрасываются. Операция `cover` читает обложку из
индекса. Это устраняет повторное чтение и разбор файлов UI-ом и делает «живое
сканирование» невозможным.

Альтернатива — кэш обложек отдельными файлами по ключу путь+mtime — отклонена:
лишняя сущность вне индекса; BLOB проще и самодостаточен. Рост размера индекса
приемлем; при необходимости позже добавим хранение миниатюр (это станет просто
следующей миграцией).

### D3. Прогресс: объём известен до чтения

Перед обработкой source-плагин делает дешёвый обход (`list_files`, только имена и
метаданные), сравнивает с индексом и получает `total` — число книг к
чтению/перечитыванию. Затем обрабатывает книги по одной и публикует событие
`{done, total}` через host-функцию `emit_event` (существующий opaque relay
`plugin::bus`/Tauri). UI слушает событие и рисует прогресс-бар. При актуальном
индексе `total = 0`, событий нет, открытие мгновенное.

Альтернатива — неопределённая «крутилка» — отклонена: пользователь не понимает
масштаб. Альтернатива — фоновое построение с постепенным наполнением — отклонена
пользователем как дезориентирующая.

### D4. Один проход, без фонового дозаполнения

Индекс строится синхронно в рамках открытия, но с прогрессом. Список не
наполняется постепенно. Это соответствует ожиданию «открыл — увидел прогресс —
получил готовую библиотеку».

### D5. Совместимость с существующими индексами

Существующие базы имеют `PRAGMA user_version = 1` и таблицы текущей схемы.
Первый набор миграций делается так, чтобы версия 1 соответствовала уже
существующей схеме, а добавление таблицы `covers` — версия 2. Тогда существующие
индексы дополняются без потери данных, а свежие применяют миграции с нуля.
Плагин остаётся источником истины по схеме; ядро не участвует.

## Risks / Trade-offs

- [Рост индекса из-за обложек] → Отдельная таблица; при необходимости позже
  храним миниатюры (новая миграция). Приемлемо для локальной библиотеки.
- [Стоимость прогресс-событий] → Одно событие на книгу дёшево; при необходимости
  троттлинг каждые N книг, не меняя контракт `{done, total}`.
- [Неудачная миграция] → Применение в транзакции; при ошибке — полная перестройка
  без частично изменённой схемы.
- [Старые индексы] → Версия 1 = текущая схема, миграция 2 добавляет `covers`;
  иначе перестройка.
- [Прогресс при переключении библиотек] → Событие содержит путь/провайдера, UI
  фильтрует по открываемой библиотеке.

## Migration Plan

1. Общий crate миграций + тесты.
2. `library`: миграции (v1 текущая схема, v2 `covers`), хранение обложки,
   `cover` из индекса, прогресс.
3. `library-calibre`: то же.
4. `emit_event` в host-функциях source-плагинов (build script); контракт.
5. UI: прогресс-бар при открытии.
6. Документация и полный набор проверок.

Откат — возврат к прежней ревизии; индексы перестраиваются из внешней библиотеки,
внешние файлы не изменяются.

## Open Questions

- Нужен ли троттлинг прогресс-событий и на каком объёме.
- Хранить ли позже миниатюры обложек вместо полных байтов.
