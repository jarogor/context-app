## Context

См. `proposal.md` — Why. Текущее состояние, важное для решения:

- Механизм плагина рабочего места уже введён
  (`openspec/specs/workplace-content-plugins`): манифест объявляет `formats` и
  относительный `viewer`, ядро отдаёт файл модуля строкой, приложение вставляет
  его в `<iframe sandbox="allow-scripts" srcdoc=…>` и обменивается сообщениями
  через канал `texture-workplace`. Реализован только образец `workplace-demo`.
- Чтение EPUB идёт другим путём: source-плагин `library` разбирает файл в главы
  HTML, `ReaderPage` → `BookReader` считает якоря заметок смещениями символов в
  главе (`src/lib/reader/anchor.ts`). Нижняя панель — масштаб и прогресс.
- Модель заметки (`src/lib/notes.ts`) хранит непрозрачный `anchor` строкой и
  поля `quote`, `chapter`, `percent`, `page`; `notePlace` уже показывает
  «Стр. N», а сортировка списка умеет страницы. Хранилище заметок opaque
  (`notes.store@1`), менять его не нужно.
- Вкладка рабочего места (`src/lib/workplace.ts`, `workspace_state.rs`) хранит
  `path`, `title`, `format`, `zoom`, `position` (процент) и `mode`.
- Проверено опытом (Chromium, песочница `allow-scripts`):
  - создание worker из `blob:`-адреса разрешено, из `url:` — запрещено
    (`origin 'null'`);
  - pdf.js, загруженный из blob-адреса с `workerSrc` = blob, поднимает fake
    worker и рендерит страницу — работает без сети и без файловой системы;
  - кастомный протокол в `iframe` на Linux/WebKitGTK не грузится
    (tauri-apps/tauri#12767, «resource requested insecurely») — целевая
    платформа проекта, поэтому «служебный URL» как отдельная схема непригоден.

## Goals / Non-Goals

**Goals:**

- Дать PDF тот же пользовательский функционал, что у EPUB: открытие, листание по
  страницам, масштаб, заметки-цитаты с выделением и подсветкой, восстановление
  страницы и масштаба вкладки.
- Сохранить архитектуру: формат рисует плагин рабочего места; ядро не знает о
  PDF; управление и панели принадлежат приложению.
- Сохранить изоляцию модуля рисования (песочница без сети, ФС и приложения) при
  модуле из нескольких файлов.

**Non-Goals:**

- Установка сторонних плагинов рабочего места из стора и их многотомный модуль —
  отдельный последующий шаг; здесь модуль поставляется вместе с приложением.
- Распознавание текста (OCR) в сканах без текстового слоя: заметка создаётся по
  имеющемуся текстовому слою.
- Комментарии пользователя к цитате и редактор заметок — вне рамок.
- PDF-специфичная логика в ядре (форматы, страницы, аннотации) — не вводится.

## Decisions

### D1. Модуль рисования — набор файлов, помещаемый в песочницу как blob-адреса

Ядро даёт приложению список файлов каталога модуля (безопасно, только внутри
каталога плагина) и их содержимое в base64. Приложение вставляет точку входа
модуля в `<iframe sandbox="allow-scripts">` как `srcdoc`, а по запросу модуля
передаёт ему байты остальных файлов; **blob-адреса создаёт сама песочница** и
импортирует из них движок и worker. Сеть не задействована, файловая система
недоступна, прямых URL/схем нет.

Ключевое ограничение, проверенное опытом: blob-адрес, созданный родительским
документом, в песочнице с `allow-scripts` (origin `null`) не загружается
(«Not allowed to load local resource»); blob, созданный внутри песочницы,
загружается успешно. Поэтому байты передаются в песочницу, а адреса — её забота.
`<base href>` на blob-каталог невозможен: у blob-адресов нет структуры каталога,
поэтому относительные ссылки плагин разрешает сам по переданной карте файлов.

Альтернативы:

- **Служебный URL (`texture-plugin://…`) как отдельная схема.** Отклонено: в
  `iframe` на Linux/WebKitGTK такая схема не грузится (tauri#12767). На macOS
  работает — расхождение платформ недопустимо.
- **Blob-адреса, созданные приложением и переданные в `srcdoc`/`<base>`.**
  Отклонено: родительские blob в песочнице не грузятся (проверено).
- **Отдача плагина из `public/plugins/…` (тот же origin).** Отклонено: работает
  только для поставляемых плагинов, ломает модель установленных пакетов и
  ослабляет изоляцию.
- **Инлайн всего модуля в один `srcdoc`.** Отклонено: библиотека pdf.js — сотни
  килобайт, раздувание строки и невозможность переиспользовать worker.

### D2. Движок — pdf.js, worker — fake/блоб

Рендер — pdf.js (`pdfjs-dist`), поставляется в составе плагина. В песочнице
worker поднимается из blob-адреса либо на главном потоке (fake worker); оба пути
проверены. Ресурсы, которые pdf.js при необходимости тянет по сети (стандартные
шрифты, cMaps), не обязательны для базового рендера; документ без них
отображается. Это осознанный компромисс ради отсутствия сети.

Альтернативы: нативный рендер в Rust (pdfium/mupdf) — тяжёлая зависимость и
знание формата в ядре, отклонено решением 2026-09-28; встроенный просмотрщик ОС —
не даёт заметок и состояния.

### D3. Обмен — расширение минимального протокола

Сообщения остаются opaque для ядра и расширяются:

- приложение → плагин: `open` (+ начальная страница и масштаб), `zoom`,
  `goto` (страница либо заметка), `notes` (список якорей текущей книги);
- плагин → приложение: `ready`, `capabilities` (масштаб, страницы, выделение),
  `state` (текущая страница, всего страниц, масштаб), `quote` (новый якорь
  выделения), `error`.

Якорь заметки страничного формата непрозрачен для ядра и хранится строкой, как
и у EPUB. Панель заметок, хранилище и отображение места (`Стр. N`) переиспользуются.

### D4. Якорь страничного формата — страница, прямоугольники и цитата

Для PDF якорь адресует страницу и набор прямоугольников выделения в долях
размера страницы (не в пикселях), поэтому не зависит от масштаба, зума и размера
окна, и восстанавливается точно. Цитата хранится рядом. Прежний текстовый якорь
EPUB не меняется; `parseAnchor` расширяется распознаванием страничного вида при
сохранении обратной совместимости.

Альтернатива: повторно использовать символьные смещения EPUB — неприменимо,
у PDF нет глав и стабильного текстового индекса до рендера.

### D5. Панель страниц — приложение, страница — состояние вкладки

Навигацию по страницам (номер, ввод номера, вперёд/назад, всего страниц) рисует
приложение из дизайн-системы, как масштаб и прогресс. Позиция чтения остаётся
совместимой: `position` вкладки выражает долю прочитанного в процентах, а
текущая страница выводится из состояния плагина; для восстановления приложение
передаёт плагину начальную страницу (вычисленную из доли) при открытии.

Альтернатива: добавить отдельное поле `page` в вкладку — избыточно до появления
форматов без процентов; при необходимости вводится позже.

## Risks / Trade-offs

- [Каскад blob-адресов модуля] → Точка входа грузится как `src` с `<base>` на
  blob-каталог; проверяется e2e-тестом с несколькими файлами модуля.
- [Размер pdf.js в составе плагина] → Хранится один раз в ресурсах; сборка
  минифицированного билда; без сети и загрузки с CDN.
- [Сканы без текстового слоя] → Заметка-цитата по такому PDF невозможна; чтение,
  листание и масштаб работают. Задокументировано как ограничение, не ошибка.
- [Изоляция при fake worker] → Worker на главном потоке внутри песочницы; доступа
  к приложению и ФС нет, обмен прежний.
- [Расхождение платформ] → Выбран blob-подход, проверенный в песочнице; кастомный
  протокол отвергнут из-за Linux.

## Migration Plan

Миграции данных нет. Порядок: расширить ядро (файлы модуля) → научить приложение
собирать модуль из blob-адресов и расширить протокол → собрать и развернуть
плагин `workplace-pdf` → страничная панель и якорь заметки → тесты и документация.
EPUB работает прежним путём. Откат — возврат ветки; внешних плагинов рабочего
места нет, данные не мигрируются.

## Open Questions

- Точная форма страничного якоря (прямоугольники vs текстовые смещения в слое
  страницы pdf.js) — уточняется при реализации плагина; обе формы непрозрачны
  для ядра и на спеки не влияют.
- Нужен ли плагину собственный WASM-модуль для метаданных/оглавления — решается
  после первого рабочего рендера; на текущие задачи не влияет.
