## Context

См. proposal.md — Why. Текущее состояние: source-плагины (`src-wasm-plugins/library`,
`library-calibre`) хранят построенный каталог целиком в служебном состоянии через
host-функции `state_read`/`state_write` (JSON-файлы `library-state.json`,
`calibre-state.json`). Плагины собраны под `wasm32-unknown-unknown`: без WASI и
сети, доступ к файлам — только через host-функции ядра. Значит SQLite физически
может предоставить только ядро.

Дополнительное ограничение, обнаруженное при анализе: `storage_root` — это общий
каталог состояния приложения (`app-state`), одинаковый для всех библиотек, а
`STATE_KEY` у плагина постоянный. Поэтому состояние источника сейчас фактически
не привязано к библиотеке и перезаписывается при открытии другой. Контракт
`library-index-cache` уже требует привязки к каноническому корню — это нужно
исправить в рамках изменения.

## Goals / Non-Goals

**Goals:**

- Дать плагинам opaque-доступ к SQLite в хранилище, изолированном на библиотеку
  и провайдера.
- Позволить source-плагинам строить индекс инкрементально: не перечитывать
  неизменённые файлы.
- Исправить привязку служебного состояния источника к каноническому корню.
- Сохранить принципы plugin-first и opaque-контрактов: ядро не знает схемы.

**Non-Goals:**

- Watcher и фоновая синхронизация в реальном времени (`library-index-cache` и
  без того описывает их как будущее; здесь только актуализация при открытии и по
  запросу).
- Фоновое индексирование с публикацией событий обновления карточек.
- Перенос портируемого собственного режима (`library-storage`, `portable.rs`) —
  у него отдельная модель «библиотека = директория».
- Отказ от `state_*`: функция остаётся для базовых плагинов и прочего состояния.

## Decisions

### D1. Generic SQL host API, а не структурный индекс

Ядро предоставляет `sql_execute(sql, params)` и `sql_query(sql, params)`.
`params` — JSON-массив скаляров; `sql_query` возвращает JSON-массив объектов
«столбец → значение». Ядро исполняет запрос и не интерпретирует SQL, схему и
данные. Альтернативы: (а) структурный API `index_upsert`/`index_search` — требует
от ядра знания модели книги, нарушает plugin-first; (б) SQLite внутри WASM —
практически недоступен из-за отсутствия WASI FS и накладных расходов. Generic API
совпадает с принципом opaque-контрактов и повторяет решение из «Журнала решений»
ROADMAP.

### D2. База вне библиотеки, ключ — провайдер и канонический корень

Файл SQLite лежит в служебной области приложения, а не в директории библиотеки.
Имя: `<storage_root>/<plugin_id>/<sha256(canonical sandbox_root)>/index.sqlite`.
`plugin_id` берётся из манифеста загруженного плагина, `sandbox_root` — активный
корень библиотеки. Это сохраняет read-only внешнего источника и одновременно
исправляет общий `STATE_KEY` (D-контекст). Альтернатива — база внутри библиотеки
(для портируемости) — отклонена: конфликтует с read-only и с моделью `state_*`.

### D3. Соединение на плагин, ленивое открытие, сериализация

`HostState` получает путь к базе и лениво открывает `rusqlite::Connection` при
первом SQL-вызове; соединение защищено мьютексом `HostState`. Вызовы сессии
сериализуются ядром, поэтому транзакции (`BEGIN`/`COMMIT` через `sql_execute`) не
пересекаются. Ошибка SQL возвращается как ошибка вызова, не роняя сессию.

### D4. Инкрементальная актуализация по `fs_list_dir` с метаданными

`fs_list_dir` дополнительно отдаёт для файлов `size` и `mtime_ms` (без чтения
содержимого). Плагин хранит эти значения в индексе; при открытии обходит дерево
по именам, сравнивает метаданные и перечитывает только новые и изменённые файлы,
а исчезнувшие удаляет. Формат метаданных — часть host-контракта (delta
`plugin-system`). Datetime берётся из `fs::metadata`, при недоступности — `null`.

### D5. Схема индекса принадлежит плагину

Плагин сам создаёт таблицы, ведёт `PRAGMA user_version` для миграций и решает,
как хранить книги/авторов/файлы. Ядро не знает ни одной таблицы. Прежнее
JSON-состояние не читается: при отсутствии/несовместимости БД плагин выполняет
полную перестройку (и может удалить старый JSON через `state_delete`).

## Risks / Trade-offs

- [Сериализация JSON через границу WASM на больших каталогах] → Начальный объём
  разумный (сотни книг); при росте — пагинация `sql_query` и/или бинарный формат.
- [Повреждение файла БД] → Ошибка SQL диагностируется; плагин может удалить базу
  и перестроить индекс; внешняя библиотека не затрагивается.
- [Смена формата индекса между версиями плагина] → `PRAGMA user_version`;
  несовместимая версия = полная перестройка.
- [Разные ОС дают разный mtime] → При недоступности метаданных поле `null`,
  плагин перечитывает файл; корректность важнее экономии.
- [Транзакции и параллельные вызовы] → Сессия сериализована мьютексом; при
  будущем параллелизме потребуется `sql_batch`/уровень транзакций.

## Migration Plan

1. Добавить `rusqlite` (bundled) в ядро, host-функции и хранилище на сессию.
2. Перевести generic-плагин `library` на SQLite и инкрементальный скан.
3. Перевести `library-calibre` тем же API.
4. Обновить документацию и контракт; прогнать проверки.

Откат — возврат к прежней ревизии; JSON-состояние не мигрируется, данные
перестраиваются из внешней библиотеки. Внешние библиотеки не изменяются.
