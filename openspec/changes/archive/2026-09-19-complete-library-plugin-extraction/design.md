## Context

См. `proposal.md` — Why. Сейчас контракт v2 уже умеет вызывать source-плагин с действиями `probe`, `scan` и `scan_book`, а ядро содержит `sources/` с DTO, локальным индексом, SQLite-каталогом и watcher. `Library` и команды напрямую используют эти детали: определяют внешний режим, загружают индекс, строят каталог и решают, какой участок пересканировать. Базовый WASM-плагин пока отвечает только за обход файловой системы и построение списка книг.

Ограничения: ядро не является библиотечным приложением и не содержит доменных моделей книг; существующие пользовательские сценарии должны сохраниться через plugin protocol; source-плагины работают в WASM без WASI и получают файловый доступ только через host-функции; портируемые библиотеки и обычные extension-плагины не должны зависеть от конкретного source-плагина. Уведомления и настройки будут отдельными базовыми плагинами в будущих изменениях и не входят в текущую реализацию.

## Goals / Non-Goals

**Goals:**

- Сделать source-плагин владельцем распознавания, состояния индекса, построения каталога и алгоритма синхронизации.
- Оставить в ядре только общий plugin runtime, sandbox, lifecycle плагинов, host API и маршрутизацию opaque запросов/ответов.
- Ввести версионируемый протокол с атомарными ответами каталога, диагностируемыми ошибками и явной моделью возможностей source-плагина.
- Перенести реализацию для источника `library` в WASM-крейт и сохранить поддержку существующей структуры директорий без записи в неё.
- Сохранить рабочее пользовательское поведение без сохранения library-specific реализации в ядре.
- Обеспечить тестируемость контракта отдельно от тестов конкретного сканера и индекса.

**Non-Goals:**

- Изменение пользовательского формата портируемой библиотеки или добавление записи во внешние каталоги.
- Создание универсального SQL или файлового индекса в runtime, которым обязаны пользоваться все source-плагины.
- Поддержка нескольких source-плагинов одновременно для одной открытой директории.
- Реализация уведомлений, настроек и других базовых плагинов: текущий change только не блокирует их будущий lifecycle.
- Изменение пользовательских сценариев и форматов данных library-плагина сверх необходимого для переноса.

## Decisions

### Source-плагин как stateful owner

Source-плагин получает операции `probe`, `open`, `catalog`, `sync` и `capabilities` через `invoke`. `open` принимает корень и сведения о доступном внешнем хранилище состояния, а возвращает идентификатор сессии, статус и полный согласованный каталог. `sync` принимает изменения или запрос проверки и возвращает новый полный snapshot каталога с версией состояния. `catalog` возвращает последний snapshot без сканирования.

Это отделяет ядро от алгоритма индекса. Альтернатива — оставить `scan_book` и передавать книги в ядро — отклонена, потому что тогда ядро продолжает владеть fingerprint, удалениями, атомарностью и политикой полной перестройки.

### Opaque plugin protocol вместо каталога в ядре

Протокол использует версионируемые request/response DTO lifecycle-плагина. Нейтральные данные могут содержать идентификаторы, отображаемые поля и относительные ссылки, но ядро трактует payload только как opaque результат контракта. Преобразование в карточки книг, поиск, чтение, обложки, системное открытие, сортировка и выдача команд выполняются внутри `library`-плагина.

Плагин может возвращать полный согласованный snapshot или специализированный ответ операции. Ядро не строит из snapshot SQLite, не сохраняет его в собственный индекс и не вызывает отдельный read adapter. Это позволяет в будущем подключать плагины уведомлений и настроек без добавления предметных моделей в ядро.

### Внешнее состояние хранится через host storage

Source-плагину предоставляются read/write host-функции только для служебного хранилища приложения, отделённого от корня библиотеки. Плагин не получает произвольный путь и не может записывать в источник. Runtime связывает storage с идентификатором канонического корня и именем source-плагина; версии формата и атомарность замены состояния контролирует плагин.

Альтернатива — разрешить плагину создавать `.booklib` в корне источника — отклонена из-за требования read-only и риска загрязнить сторонние каталоги.

### Runtime остаётся транспортным слоем

`PluginRuntime` отвечает за манифест, контракт, вызов, sandbox и маршрутизацию host-функций. Он не знает семантику книг, не строит SQLite-схему и не выбирает алгоритм синхронизации. Координатор ядра ограничивается выбором source-плагина, передачей запроса и проверкой схемы ответа.

Ядро хранит только активный plugin session, статус lifecycle и последний opaque response для доставки клиенту. Команды списка, поиска, чтения, обложки и открытия являются маршрутизаторами запросов к плагину. Проверка путей, чтение файлов, работа с индексом и watcher выполняются через host API и код `library`-плагина; ядро предоставляет только sandbox и системные ограничения.

### Граф зависимостей плагинов

Манифест каждого плагина может объявлять capabilities в формате `имя@версия` через поля `provides` и `requires`. Runtime строит граф по этим строкам, проверяет отсутствующие и дублирующие capabilities, обнаруживает циклы и выполняет топологическую сортировку. Для вызова зависимости runtime выбирает плагин-поставщик и передаёт ему opaque имя операции и JSON payload. Ядро не знает, что означает capability или операция.

Прямой поиск и вызов плагинов друг другом не используется: маршрутизация через runtime сохраняет единые права доступа и позволяет заменять поставщика без изменения вызывающего плагина. Список предметных capabilities не зашивается в ядро и приходит только из манифестов.

### Явная версия протокола и миграция старого индекса

Контракт повышается до следующей версии. Старые плагины, реализующие только `probe`/`scan`/`scan_book`, не считаются совместимыми с новым lifecycle и отклоняются с понятной ошибкой. Старый `.booklib` не импортируется ядром: `library`-плагин сам решает, может ли использовать старое состояние, или выполняет полное построение нового состояния во внешнем storage.

Такой вариант предпочтительнее скрытой совместимости в ядре, поскольку иначе библиотечная логика снова появится в двух местах. Миграция должна быть ограничена плагином и удаляться после подтверждения корректности нового snapshot.

## Risks / Trade-offs

- [Risk] Увеличится объём данных между WASM и ядром при возврате полного snapshot → ограничить DTO только данными каталога, добавить версию и проверку размера ответа, а частичную работу выполнять внутри плагина.
- [Risk] Ошибка source-плагина может сделать каталог временно недоступным → сохранять последний согласованный snapshot в runtime-состоянии и показывать диагностируемое состояние синхронизации без потери чтения.
- [Risk] Версионная миграция старых индексов потребует полного сканирования → документировать fallback, выполнять его только source-плагином и не изменять исходную директорию.
- [Risk] Чтение файлов по путям из snapshot может привести к path traversal → принимать только относительные пути, канонизировать их на host-границе и проверять принадлежность активному корню перед каждым чтением.
- [Risk] Другие будущие source-плагины могут требовать возможностей, которых нет у `library` → сделать capabilities частью контракта и не кодировать конкретные форматы в ядре.

## Migration Plan

1. Зафиксировать DTO и версии протокола, добавить контрактные тесты для валидных, неполных и несовместимых ответов.
2. Добавить host storage и расширить runtime так, чтобы sandbox файлов библиотеки и служебное хранилище были раздельными.
3. Перенести индекс, каталог, fingerprint, watcher-события, операции пользовательского каталога и полную/частичную синхронизацию в `src-wasm-plugins/library`; сохранить тесты поведения на уровне плагина.
4. Переписать `Library` и команды на общий plugin lifecycle protocol, удалить прямые зависимости ядра от `ExternalBook`, `LibraryIndex`, `sources::catalog`, `sources::coordinator`, SQLite virtual catalog и watcher.
5. Пересобрать ресурсный плагин `library`, обновить манифест и проверить открытие существующей внешней директории, повреждённого состояния, read-only сценариев и всех текущих пользовательских операций через plugin protocol.
6. Обновить документацию и основной набор спецификаций после прохождения всех проверок.

Откат выполняется по границам: до шага 4 можно откатить только протокол и плагин; после шага 4 требуется вернуть старый runtime и ядро одним согласованным изменением, поскольку промежуточные версии контрактно несовместимы.
