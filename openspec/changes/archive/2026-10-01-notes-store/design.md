## Context

Базовые плагины «Текстуры» — WASM-модули в `src-wasm-plugins/`, загружаемые
app-level `AppPluginHost` из `src-tauri/resources/base-plugins/`. Плагин
экспортирует `invoke`, получает host-функции `state_read`/`state_write`/
`state_delete`/`emit_event`/`now_millis` и обслуживает opaque-операции через
capability. Приложение вызывает их generic-командой
`invoke_base_plugin_operation`, не интерпретируя payload. Образцы — плагины
`settings` (capability `settings.store@1`, состояние в `settings.json`) и
`notifications` (`notifications.journal@1`).

См. `proposal.md` — Why. Требования — в
`specs/notes-store/spec.md`.

Книги в рабочем месте адресуются парой `bookId` + `format` (см.
`src/lib/workplace.ts`), вкладки хранятся реестром рабочих мест
(`workspace-manager`). Стабильной сквозной идентификации произведения ещё нет —
домен `book-identity` помечен `❓` и отложен.

## Goals / Non-Goals

**Goals:**
- Дать наборы заметок как самостоятельное хранилище под opaque-операциями, без
  знания ядра о форматах и моделях.
- Сохранить заметки отдельно от книги, в служебном состоянии плагина.
- Дать контракт, достаточный для будущего `editor` (CRUD наборов и заметок,
  выборка по книге и по набору, событие об изменении).

**Non-Goals:**
- UI редактора, реестр всех наборов, поиск и подборки (`editor`,
  `notes-library`).
- Импорт/экспорт и обмен наборами (`notes-io`).
- Стабильная идентификация книги (`book-identity`) и SQLite-хранилище заметок.
- Переключение наборов «на вкладку» — набор адресуется книгой, не вкладкой.

## Decisions

### Базовый плагин, а не модуль ядра

Заметки — базовый плагин (`kind: "base"`) по принципу «Plugin-first»: привязка
заметок живёт в плагине, ядро только маршрутизирует opaque-операции.
Альтернатива — модуль ядра по образцу `workspace_state` — отклонена как
возврат к сваливанию доменов в ядро.

### Capability и состояние

Capability — `notes.store@1`. Состояние — целиком один JSON под ключом
`notes.json` через `state_read`/`state_write` (как `settings.json`). Полная
перезапись проста и достаточна для объёма личных заметок; дебаунс-сохранение
обеспечивает вызывающая сторона.

```json
{
  "version": 1,
  "sets": [
    {
      "id": "ns-...",
      "book_key": "<opaque>",
      "name": "Набор",
      "created_at_millis": 0,
      "notes": [
        {
          "id": "note-...",
          "anchor": "<opaque>",
          "quote": "",
          "chapter": "",
          "percent": null,
          "text": "",
          "created_at_millis": 0,
          "updated_at_millis": 0
        }
      ]
    }
  ]
}
```

`anchor` и `book_key` хранятся как непрозрачные строки: плагин заметок их не
разбирает, а возвращает вызывающей стороне. `quote`/`chapter`/`percent` —
отображаемые метаданные места, заполняет плагин формата; `percent` допускает
отсутствие.

### Ключ книги

Наборы группируются по `book_key` — строке, которую передаёт вызывающая сторона
и которую плагин заметок не интерпретирует. Сейчас это будет составной ключ
библиотеки и книги, формируемый оболочкой; после появления `book-identity`
источник ключа сменится без правки плагина заметок.

### Операции

`invoke` принимает `{ action, payload }`. Операции: `list_sets` (по `book_key`),
`get_set` (по `set_id`), `create_set`, `rename_set`, `delete_set`, `add_note`,
`update_note`, `delete_note`. Ответ — JSON; отказ — строка ошибки. Список наборов
возвращает идентификатор, имя и число заметок; `get_set` — набор целиком.
Плагин заметок проверяет существование набора и непустоту имени на своей стороне,
чтобы правила не размазывались по клиентам.

### Идентификаторы и время

Плагин сам генерирует идентификаторы (`ns-`/`note-`) и берёт время через
`now_millis`, поэтому корректность не зависит от клиента. Существующие данные при
чтении нормализуются (неизвестные поля игнорируются, обязательные заполняются
безопасными значениями) — как в других плагинах.

### Событие

При любом изменении плагин публикует `notes:changed` через `emit_event`, передавая
`book_key` и (если применимо) `set_id`. Этого достаточно, чтобы открытые
представления обновлялись, не запрашивая хранилище вслепую.

### Миграции нет

Прежних данных заметок не существует, поэтому переносить нечего. Контракт
версионируется полем `version` в состоянии на будущее.

## Risks / Trade-offs

- [Ключ книги нестабилен: смена идентификатора книги в библиотеке осиротит
  наборы] → ключ непрозрачен и поступает извне, поэтому смена источника ключа
  после `book-identity` не ломает плагин; до этого ключ формирует оболочка как
  составной «библиотека + книга».
- [Одна книга из разных библиотек получит разные наборы] → это следует из
  открытого вопроса «общие заметки или у каждой библиотеки свои»; решение
  отложено до `library-manager`/`book-identity` и не меняет контракт плагина.
- [Перезапись всего JSON на каждое изменение не масштабируется] → объём личных
  заметок невелик, а поиск и масштаб — домен `notes-library`; SQLite остаётся
  возможным будущим хранилищем за тем же opaque-контрактом.
- [Слабая согласованность при одновременной работе из разных рабочих мест] →
  состояние принадлежит одному процессу; клиент сохраняет через дебаунс, конфликты
  разрешаются последней записью.

## Migration Plan

1. Добавить плагин `src-wasm-plugins/notes-store/` и член workspace.
2. Собрать и развернуть артефакт в `src-tauri/resources/base-plugins/notes-store/`
   через `scripts/build-wasm-plugins.sh`.
3. Добавить константу capability `notes.store@1` в контракт ядра.
4. Откат — удалить каталог плагина; других изменений хранилища нет.

## Open Questions

- Обмен наборами (`notes-io`) и его формат — откладывается, контракт плагина от
  него не зависит.
- SQLite вместо JSON под тем же opaque-контрактом — возможное будущее.
- Связь заметок с библиотекой (общие или раздельные) — решается в
  `library-manager`/`book-identity`.
