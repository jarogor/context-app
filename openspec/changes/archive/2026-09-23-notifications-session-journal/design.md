## Context

См. `proposal.md` — Why. Журнал хранится в служебном состоянии плагина (`journal.json`) и восстанавливается при старте. Требуется сессионное поведение: старт — пусто, завершение — записи исчезают.

## Goals / Non-Goals

**Goals:**

- Каждый запуск начинается с пустого журнала.
- Минимальное изменение: ядро сбрасывает журнал через существующую операцию `clear`.

**Non-Goals:**

- Удаление механизма служебного состояния плагина (он нужен другим плагинам).
- Очистка журнала при завершении приложения (достаточно сброса при старте).

## Decisions

### 1. Сброс журнала при старте из ядра

`AppPluginHost::reset_notifications()` находит провайдера capability `notifications.journal@1` и вызывает opaque-операцию `clear`. Вызов выполняется в `lib.rs` сразу после загрузки базовых плагинов и до записи событий загрузки. При отсутствии провайдера вызов безвреден.

Альтернатива — хранить журнал только в памяти плагина без `state_*` — отклонена: поведение зависит от переиспользования инстанса WASM и менее прозрачно; сброс через уже существующую операцию явный и тестируемый.

## Risks / Trade-offs

- [Ядро знает имя операции `clear`] → ядро уже вызывает `publish` по capability; добавление `clear` симметрично.
- [Записи теряются при аварийном завершении] → это и есть желаемое поведение (журнал сессионный).

## Migration Plan

1. Добавить `reset_notifications` и вызвать при старте.
2. Обновить спеку `notifications`, удалить неиспользуемую страницу плагина.
3. Проверить тесты и сборку.
