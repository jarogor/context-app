## Context

См. `proposal.md` — мотивацию. Здесь только состояние и ограничения, влияющие на
подход.

Текущее состояние (проверено по коду):

- Общего каркаса страницы в дизайн-системе нет: поиск `PageShell / ListPage /
  SearchField` в пакете пуст.
- Три страницы-списка собраны по-разному:
  - `LibrariesPage.svelte` — `p-6`, заголовок `<h1>Библиотеки</h1>`, создание
    полноширинной кнопкой `Button`, **поиска нет**, удаление — отдельной
    `DeleteButton` сбоку;
  - `WorkspacesPage.svelte` — `p-6`, создание `Input`+`AddButton` сверху, поиск
    полноширинным `Input` ниже, список строк, действия — `ActionMenu`;
  - `NotesLibraryPage.svelte` — `mx-auto max-w-4xl p-4`, поиск полноширинным
    `Input`, сворачиваемые секции, действия — `ActionMenu`;
  - `LibraryPage.svelte` (книги) — `p-6`, поиск как `<label>Поиск</label>` +
    `Input class="max-w-[420px]"`, сетка `repeat(auto-fill,minmax(160px,1fr))`;
    **в объём не входит** (D6).
- Дублирование: `WorkspacePickerDialog.svelte` почти дословно повторяет поиск и
  создание из `WorkspacesPage.svelte`.
- Адаптивность почти не применяется: во всём `src` только `sm:flex-row`
  (страница книги) и `max-[899px]` (панель заметок, `App.svelte`), плюс
  `auto-fill` сетки обложек. Нет единых точек перелома и токена ширины.
- Дизайн-система собрана из компонентов `packages/ui/src/components/*`, экспорт —
  `packages/ui/src/index.ts`, токены — `packages/ui/src/tokens.css` (блок
  `@theme inline` превращает токены в утилиты Tailwind v4).
- `AGENTS.md`, раздел «Фронтенд», уже требует: «одна функциональность — один
  компонент, переиспользуемый везде» и запрещает собственные `<style>`-блоки.

Ограничение: `app-shell` уже показывает название раздела в шапке
(`sectionTitle`), а `LibrariesPage`/`LibraryPage` дублируют заголовок на самой
странице.

## Goals / Non-Goals

**Goals:**

- Ввести в `@texture/ui` переиспользуемые каркас страницы-списка и компонент
  поиска/создания и применить их на всех четырёх страницах-списках.
- Задать единый, проверяемый набор точек перелома и адаптивное поведение.
- Устранить дублирование поиска/создания в `WorkspacePickerDialog`.
- Зафиксировать норму адаптивной вёрстки в правилах проекта.

**Non-Goals:**

- Не менять модели данных, хранилища, переходы и бизнес-логику.
- Не реализовывать подборки/группировку библиотек и наборов (заложено, но не
  делается).
- Не переделывать модальные поверхности, не являющиеся списками (настройки,
  уведомления), кроме устранения конкретного дубля поиска в диалоге выбора места.
- Не вводить дизайн-токены для брейкпоинтов как JS-константы: Tailwind v4 и так
  даёт единые модификаторы; достаточно зафиксировать их состав в спеке и
  использовать классы.

## Decisions

### D1. Каркас страницы-списка — компонент дизайн-системы `PageShell`

Новый компонент в `packages/ui/src/components/` с пропсами-слотами: панель формы
(слева на широком окне), панель действий, область списка, состояние
загрузки/ошибки/пустоты. Каркас задаёт единый внешний контейнер с переменной
шириной и адаптивными отступами. **Название раздела не рисуется** — его показывает
шапка (`app-shell`).

Альтернатива: общий CSS-класс-утилита без компонента. Отклонена: часть страниц
несёт логику состояний (загрузка/ошибка/пусто), а правило проекта требует общих
компонентов, а не разметки «по классу».

### D2. Поиск с созданием — один компонент `SearchCreate`

Объединяет поле поиска и (опционально) строку создания: поле имени + `AddButton`.
Управляется пропсами `query` (bindable), `onCreate`, `onSearch`,
`createPlaceholder`, `searchPlaceholder`, `disabled`. Сейчас одинаковый блок живёт в
`WorkspacesPage` и `WorkspacePickerDialog` — оба переводятся на него.

Альтернатива: два отдельных компонента (поиск и создание). Отклонена: они почти
всегда используются вместе, а по отдельности создают соблазн снова разойтись.

### D3. Адаптивность — на уровне страницы, а не пунктов

Раскладку задаёт каркас `PageShell`: панель формы (`form`) и область списка. На
`lg:` форма уходит колонкой влево фиксированной ширины, список занимает остаток
справа; на узком — колонки встают друг под друга (форма сверху). **Список строк
всегда остаётся вертикальным списком** — прежнее превращение пунктов в строку
(`lg:grid-cols-2`) отклонено: это не адаптивность, а искажение формы. Единый предел
ширины контента задаёт токен `--content-max-width`.

Альтернатива (первая итерация): «осознанный переход к сетке на `lg:`». Отклонена по
отзыву пользователя: список должен оставаться списком при любом масштабе.

### D4. Единый вид пункта — `ListRow` + `MetaList`

Пункт всех строковых списков (рабочие места, библиотеки, наборы заметок) рисует
`ListRow`: название акцентом сверху, метаинформация строкой под ним, действия —
`ActionMenu` справа. Метаинформация собирается из `MetaItem` (подпись + значение,
признак выделения) и своя у каждого списка: место — дата создания и «текущее»;
библиотека — провайдер, время открытия, доступность, путь; набор — книга, число
заметок, дата изменения. Клик по строке выполняет переход; действия (в т.ч.
удаление библиотеки) уходят в меню, отдельные кнопки сбоку не используются.
`ListRow` умеет `selected` (текущее/активное) и `expanded` (раскрываемый набор).

### D5. Устранение дубля — `WorkspacePickerDialog` на `SearchCreate`

Диалог перестаёт держать свою копию поиска/создания. Его поведение (поиск, создание
и сброс запроса при закрытии) сохраняется, но разметка приходит из одного компонента.

### D6. Список книг — вне объёма

`LibraryPage` (книги) не трогается: это богатый список (обложка, авторы, действия),
которому нужно **отдельное** оформление с привычными режимами «список/плитка».
Памятка внесена в `ROADMAP.md` (открытые вопросы); делается отдельным изменением.

## Risks / Trade-offs

- [Ломается вид привычных страниц] → Миграция по одной странице, каждую покрываем
  компонентным/e2e-тестом; новые общие компоненты получают свои тесты.
- [Существующие e2e опираются на разметку] → Обновляем селекторы/подписи в
  `tests/e2e/{shell,workspaces,notes}.spec.ts` вместе с миграцией.
- [Единый каркас «подрежет» специфичные страницы] → Каркас даёт только контейнер,
  панель формы, состояния и (для строк) пункт; форма содержимого остаётся за
  страницей (список книг вынесен из объёма, D6).
- [Дубль `WorkspacePickerDialog`] → Переводим на `SearchCreate` в этом же change,
  иначе правило «один компонент» остаётся нарушенным.
- [Смешение с датой/форматированием] → Не трогаем логику; только представление.

## Migration Plan

1. Добавить `PageShell`, `SearchCreate`, `ListRow`, `MetaList` в `packages/ui`,
   экспортировать, покрыть тестами; вынести общий `formatDateTime`.
2. Перевести `WorkspacesPage` (+ `WorkspacePickerDialog`) — самый явный дубль.
3. Перевести `LibrariesPage`, добавив поиск и заменив кнопку удаления меню.
4. Перевести `NotesLibraryPage`.
5. Обновить `AGENTS.md` (раздел «Фронтенд»), `_docs` и `ROADMAP.md`.

Откат: изменения представления локальны по страницам; возврат — откат коммита.
