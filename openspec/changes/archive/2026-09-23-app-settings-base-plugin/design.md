## Context

См. `proposal.md` — Why. Состояние, важное для подхода:

- App-level `AppPluginHost` загружает базовые плагины из `resources/base-plugins/` и владеет app-level `PluginRuntime`; сессия библиотеки перезагружает `PluginRuntime` при `configure`.
- `PluginManifest` уже десериализует неизвестные поля молча; `LoadedPlugin` не сохраняет декларации.
- Есть capability-маршрутизация: `PluginRuntime::invoke_capability(capability, action, payload)` и `plugin_providing`.
- Служебное хранилище плагина доступно через host-функции `state_read`/`state_write`; `emit_event` транслирует прикладные события в Tauri.
- Frontend-плагины монтируются в iframe через `PluginFrame.svelte` и общаются с оболочкой сообщениями `layout`; `App.svelte` уже содержит регион уведомлений.

## Goals / Non-Goals

**Goals:**

- Базовый плагин настроек как единственный владелец реестра секций и значений; ядро остаётся тонким транспортом.
- Декларация секций плагином без inter-plugin вызовов и без изменения кода ядра под конкретный плагин.
- Кнопка входа в настройки и отдельная страница как отдельный frontend-плагин; оболочка знает только слот-регион.
- Сквозные примеры: секция приложения (читается ядром) и секция плагина уведомлений (читается `notifications-ui`).

**Non-Goals:**

- Типизированные формы полей и авто-рендер по схеме — вне scope; значения редактируются как сырой JSON.
- Динамическая установка/обновление плагинов и горячая перезагрузка реестра без перезапуска/переоткрытия библиотеки.
- Права доступа плагинов к чужим секциям настроек.
- Изменение source-lifecycle библиотеки.

## Decisions

### 1. Схема настроек — opaque JSON в манифесте, интерпретирует плагин настроек

В `PluginManifest` добавляется `settings: Option<serde_json::Value>` с `#[serde(default)]`. Ядро не разбирает содержимое: `LoadedPlugin` сохраняет значение, а `PluginRuntime` отдаёт декларации участников через `settings_sources()`. Интерпретацию схемы выполняет только базовый плагин настроек.

Формат схемы (контракт `settings.store@1`, задаёт плагин настроек):

```json
{
  "title": "Уведомления",
  "sections": [
    {
      "id": "notifications",
      "title": "Журнал",
      "description": "Параметры журнала уведомлений",
      "defaults": { "technical_visible_default": false }
    }
  ]
}
```

Полный идентификатор секции — `<owner>.<section.id>` (например, `notifications.notifications`, `app.general`).

Альтернатива — типизированная модель схемы в ядре — отклонена: нарушает принцип минимального ядра и заставляет ядро знать модель настроек; при усложнении схемы (типы, валидация) пришлось бы менять ядро.

### 2. Capability `settings.store@1` и операции реестра

Базовый плагин `settings` предоставляет capability `settings.store@1` и операции (opaque для ядра):

- `register` — payload `{ "sources": [ { "owner", "kind", "schema" } ] }`; полностью валидирует реестр (уникальность полных id), затем атомарно заменяет его. При конфликте возвращает ошибку, не меняя прежний реестр.
- `list` — `{ "sections": [ { "id", "owner", "kind", "title", "description", "values" } ] }`.
- `get` — payload `{ "section": "<full_id>" }` → `{ "values": {...} }` (defaults, объединённые с сохранёнными).
- `set` — payload `{ "section": "<full_id>", "values": {...} }` → `{ "values": {...} }`; мержит на верхнем уровне, сохраняет, публикует `settings:changed`.

Значения лежат в служебном состоянии плагина `settings.json` как `{ "values": { "<full_id>": { ... } } }`, поэтому переживают перезапуск. Ядро вызывает операции через `invoke_capability` и не знает модель.

### 3. Сбор и перерегистрация реестра ядром

`AppPluginHost::refresh_settings_registry(session_sources: &[serde_json::Value])`:

1. Берёт `settings_sources()` app-level runtime (базовые плагины).
2. Добавляет `session_sources` (source/extension-плагины сессии), переданные вызывающим.
3. Добавляет секцию приложения: источник `{ "owner": "app", "kind": "app", "schema": APP_SETTINGS_SCHEMA }`, где `APP_SETTINGS_SCHEMA` — константа ядра с секцией `general` и `startup.welcome_notification`.
4. Если провайдера `settings.store@1` нет — безвредно выходит.
5. Иначе вызывает `register` с объединённым списком.

Точки вызова: сразу после загрузки базовых плагинов в `lib.rs` (с пустой сессией) и в `invoke_plugin_operation` после `session.configure(...)` — там доступен и `session`, и `app_host` через `AppState`. `PluginSession` получает метод `settings_sources()`, делегирующий в `runtime`.

Альтернатива — core-команда `list_settings_sections` с типизированной моделью — отклонена по той же причине минимального ядра.

### 4. Секция настроек приложения как пример

После `refresh_settings_registry` в `lib.rs` ядро запрашивает `get` секции `app.general` и читает `startup.welcome_notification` (по умолчанию `true`); при истинном значении публикует пользовательское уведомление `notify_user` до открытия библиотеки. Это единственное место, где ядро знает ключ настройки, — собственная настройка приложения, а не доменная модель.

### 5. Frontend-плагин `settings-ui` и слот в оболочке

`plugins/settings-ui/` строится по образцу `notifications-ui` (Svelte + Vite + `bridge.ts`): кнопка «Настройки» в правом верхнем углу и страница со списком секций; значения каждой секции — textarea с JSON и кнопка «Сохранить». Плагин вызывает `invoke_base_plugin_operation('settings', ...)` и подписывается на `settings:changed`.

Оболочка (`App.svelte`) добавляет регион `settings` с состояниями `button` (маленькая кнопка справа сверху, z-index выше контента) и `page` (полноэкранный слой). Регион управляется `layout`-сообщениями с `region: "settings"` тем же протоколом, что и уведомления; код UI настроек в оболочке отсутствует. `build-frontend-plugins.sh` собирает `settings-ui`.

### 6. Секция плагина уведомлений

Манифест `src-wasm-plugins/notifications/` (генерируется `build-wasm-plugins.sh`) получает поле `settings` с секцией `notifications` и `defaults.technical_visible_default = false`. `notifications-ui` при монтировании читает `get` для `notifications.notifications` и инициализирует `technicalVisible`, что демонстрирует чтение плагинной настройки. Схема секции живёт в сборочном скрипте как аргумент `deploy_plugin`, чтобы не дублировать манифест вручную.

## Risks / Trade-offs

- [Ядро всё же читает один ключ настройки приложения] → это собственная настройка приложения, а не доменная модель; при желании пример выносится в отдельный плагин позже.
- [Событие `settings:changed` доставляется через существующий bus и может задерживаться до следующего flush] → задержка не критична для настроек; при необходимости потребитель перечитывает значения при открытии.
- [Конкурентная запись значений секции] → MVP редактируется одним пользователем; `set` мержит ключи верхнего уровня, полная замена значения доступна повторным `set`.
- [Полноэкранный регион настроек перекрывает регион уведомлений] → settings-регион имеет больший z-index и закрывается кнопкой возврата; после закрытия поведение прежнее.
- [Секции от frontend-only плагинов не попадают в реестр] → ядро читает манифесты только WASM-плагинов; UI-плагины без WASM-части декларируют настройки позже через собственную WASM-обёртку, это вне scope.

## Migration Plan

1. Добавить `settings` в манифест, `LoadedPlugin` и `settings_sources()`; поведение существующих плагинов не меняется (поле опционально).
2. Ввести capability и базовый WASM-плагин `settings`; собрать артефакты.
3. Подключить `refresh_settings_registry` в `lib.rs` и `invoke_plugin_operation`; добавить секцию приложения и приветствие.
4. Добавить `plugins/settings-ui/` и регион в `App.svelte`.
5. Декларировать секцию в уведомлениях и читать её в `notifications-ui`.
6. Откат: изменение аддитивно; при необходимости убрать регион из оболочки и базовый плагин, вернув прежний состав.
