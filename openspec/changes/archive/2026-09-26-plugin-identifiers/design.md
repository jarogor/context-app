## Context

Сейчас идентичностью плагина служит его `name`: по нему строится папка установки,
ведётся дедупликация при загрузке из нескольких директорий, разрешаются зависимости
и capabilities, хранятся провайдер истории, владелец настроек и реестр активности.
Манифест (`src-tauri/src/plugin/plugin_manifest.rs`) содержит только `name`; frontend
UI-плагины тоже идентифицируются по `name`. Смена имени ломает все эти ссылки
(см. proposal.md — Why).

## Goals / Non-Goals

**Goals:**

- Ввести стабильный `id` (UUID) как единственный ключ идентичности плагина всех видов.
- Оставить `name` человекочитаемой подписью для UI и диагностики.
- Перевести на `id`: дедупликацию, зависимости, реестр активности, провайдера истории,
  владельца настроек, установку/удаление/конфликты пакетов, включение/отключение.
- Сохранить нейтральность ядра: оно по-прежнему не интерпретирует предметные модели.

**Non-Goals:**

- Обратная совместимость со старыми манифестами без `id` и с данными, сохранёнными
  под именами.
- Автоматическая миграция `disabled-plugins.json`, `library-history.json` и ключей
  настроек.
- Смена формата capability (`имя@версия`) — capabilities не трогаем.
- Реактивная перезагрузка плагинов без перезапуска (отдельное изменение).

## Decisions

### D1. `id` — обязательный UUID, `name` — подпись

Манифест получает обязательное `id: String`; валидация — разбор `uuid::Uuid::parse_str`.
Поле `name` сохраняется и используется только для отображения/логов. Альтернативы:
простой слаг (отвергнут пользователем в пользу UUID) и namespaced-строка (избыточна,
UUID уже гарантирует уникальность). Добавляем прямую зависимость `uuid` в `src-tauri`.

### D2. Папка плагина перестаёт быть идентичностью

Идентичность определяется манифестом, а не именем каталога. Встроенные ресурсные
плагины продолжают лежать в читаемых папках (`library-calibre` и т.п.), задаваемых
скриптом сборки. Установленные через стор пакеты распаковываются в подкаталог с
именем `id` пользовательского каталога, поэтому конфликт и удаление решаются без
скан-эвристик. Дедупликация загрузки — по `id` (приоритет: библиотека →
пользовательский каталог → ресурсы). `removable` определяется тем, что папка
плагина лежит в пользовательском каталоге, а не совпадением имени.

### D3. Реестр активности хранит `id`

`activation.rs` записывает `id` в `disabled-plugins.json`; фильтр загрузки сравнивает
`LoadedPlugin.id`. Записи-имена прошлых версий просто ни с чем не совпадают.

### D4. История и UI: `provider` = `id`, отдельно `provider_name`

`discovery::discover_source_plugins` начинает возвращать пары `(id, name)`.
`library_history::list(root, available, disabled_ids)` фильтрует по `id`, а в
`HistoryEntry` добавляет `provider` (id) и `provider_name` (человекочитаемое имя) для
UI. `library-ui` показывает `provider_name`, а открытие выполняет по `provider` (id).

### D5. Владелец настроек — `id` плагина

Ядро формирует opaque-декларации настроек с `owner = plugin.id`; секция приложения
сохраняет `owner = "app"`. Полный идентификатор секции `<id>.<section.id>` и ключи
значений становятся стабильными при переименовании. Заголовок для UI берётся из
декларации (`title`), а не из `owner`.

### D6. Store оперирует `id`, показывает `name`

`InstalledPlugin` и `PluginEntry` получают `id`; host-функции `store_uninstall`,
`store_set_enabled`, операции `uninstall`/`set_enabled` принимают `id`. UI стора
показывает `name`, а команды отправляет по `id`.

### D7. Без миграции

Старые данные не переводятся. Неизвестные `id` записи истории скрываются фильтром
доступных провайдеров, реестр активности их игнорирует, осиротевшие ключи настроек
остаются без владельца. Локальные служебные файлы при необходимости сбрасываются
вручную (согласовано с пользователем).

### D8. UUID фиксируются в источниках

Скрипт `scripts/build-wasm-plugins.sh` принимает `id` и подставляет в генерируемый
манифест; в нём перечислены постоянные UUID по одному на плагин. Frontend-манифесты
`plugins/*/plugin-manifest.json` и `dev_data/app-plugins/demo/plugin-manifest.json`
получают статические UUID. Идентификаторы не генерируются на каждой сборке.

## Risks / Trade-offs

- [Потеря локальных данных о активности, истории и настройках при первом запуске
  новой версии] → Сознательное решение без миграции; сброс служебных файлов вручную,
  документируется в `_docs`.
- [Случайная смена UUID при правке скрипта сборки сломает ссылки] → UUID задаются
  таблицей констант в скрипте и в статических манифестах; тесты валидации отвергают
  манифест без `id`.
- [UUID в `owner` настроек может попасть в UI] → UI строится по `title` декларации;
  проверяем, что `settings-ui` не выводит `owner` как подпись.
- [Ядро не знает о провайдерах, но теперь резолвит `provider_name` для истории] →
  резолв выполняется по манифестам через discovery, без предметных правил; при
  отсутствии провайдера запись и так скрыта.

## Migration Plan

1. Обновить манифесты и скрипт сборки, добавив UUID.
2. Перевести ядро и store на `id`.
3. Пересобрать WASM- и frontend-плагины.
4. При необходимости вручную удалить/поправить локальные
   `disabled-plugins.json`, `library-history.json` и состояние настроек.
5. Откат — возврат к прежней ревизии; новые данные при этом тоже несовместимы.
