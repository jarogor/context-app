## Context

Сейчас `Library::open` в `src-tauri/src/library/mod.rs` всегда создаёт собственную
портируемую структуру (папки `books/`, `covers/`, `plugins/` + `library.db`) и
открывает SQLite-каталог. Все команды (`list_books`, `get_cover`,
`get_book_content`) читают записи из этой БД, а пути файлов хранятся
относительными к корню библиотеки. Мотивация и требования — см. proposal.md и
спеки `calibre-library`, `library-ui`.

Пользователь уже хранит библиотеку в Calibre (структура `<Author>/<Title> (id)/`
с `metadata.opf`, файлами книг и обложками) и хочет открывать её без копирования
и без изменения файлов.

## Goals / Non-Goals

**Goals:**
- Распознавать тип директории при `Library::open`: собственная библиотека,
  Calibre-библиотека или пустая (новая) директория.
- Для Calibre-библиотеки строить виртуальный каталог в in-memory SQLite с той же
  схемой и по тем же относительным путям, переиспользуя существующие команды
  `list_books`/`get_cover` и репозиторий без их изменения.
- Добавить поиск (`search_books`), открытие книги в системном приложении
  (`open_book_in_system`) и команду идентификации режима (`get_library_info`).
- Импорт в Calibre-режиме отклонять; в UI скрывать кнопку импорта.
- Файлы Calibre-библиотеки не копировать и не менять.

**Non-Goals:**
- Запись/синхронизация метаданных между встроенным каталогом и Calibre
  (например, запись статуса прочтения обратно) — не требуется.
- Индексация в постоянное хранилище: виртуальный каталог строится заново при
  каждом запуске (см. spec «Повторное сканирование при запуске»).
- Поддержка чтения содержимого внутри приложения для Calibre-книг: чтение
  выполняется во внешнем системном приложении; встроенный read-view остаётся
  только для собственных библиотек.
- Парсинг `metadata.db` Calibre — не требуется: достаточно `metadata.opf`
  (стандарт EPUB) и структуры папок.

## Decisions

### 1. Виртуальный каталог в in-memory SQLite поверх существующей схемы

Calibre-каталог загружается в `rusqlite::Connection` в памяти
(`:memory:`), где применяется та же миграция схемы (`catalog::open_catalog`).
Записи заполняются репозиторием как при импорте: книга + авторы + файлы
(относительные пути от корня Calibre-библиотеки). Внутри `Library` хранится
`CatalogSource::{Portable(in-memory? no, файловая БД), Calibre(:memory:)}`, а
именно:

```rust
pub enum LibraryMode {
    Portable,            // собственная библиотека: library.db на диске
    CalibreVirtual,      // Calibre: in-memory БД, файлы читаются из каталога Calibre
}
```

Почему in-memory вместо новой схемы хранения:
- `list_books`, `get_cover`, `get_book_content` и репозиторий работают без
  изменений: они видят обычный `Connection` и относительные пути.
- Не нужен отдельный интерфейс/абстракция каталога — минимум кода.

Альтернатива (отвергнута): отдельный trait/интерфейс типа «каталог» с
реализациями под SQLite и под Calibre. Избыточен для текущего объёма команд и
ломает переиспользование репозитория.

### 2. Заполнение in-memory каталога через транзакцию

Сканирование собирает записи, затем один проход в транзакции вставляет
авторов/серии/теги (переиспользуются существующие), книги и файлы. Пути файлов —
относительные к корню Calibre, формат расширения — по расширению файла
(для содержимого книги приоритет EPUB/MOBI/AZW3/PDF и др.; обложка — первое
распознанное изображение `cover.*` или `metadata.opf`-cover, если файл есть
в папке книги).

### 3. Распознавание типа по структуре папок

При открытии директории проверяем в следующем порядке:
1. Есть `library.db` → собственная библиотека (`Portable`).
2. Нет `library.db`, но есть как минимум один элемент, удовлетворяющий
   типовому паттерну Calibre (папка второго уровня с `metadata.opf`) →
   `CalibreVirtual`, файлы каталога Calibre не трогаются.
3. Директория не существует или пуста → создаётся собственная структура
   (`Portable`), как и раньше.

Паттерн: два уровня вложенности `<Author>/<Title> (id)/`, внутри — `metadata.opf`
и файлы книг. Проверка ограничена одним-двумя уровнями глубины, без полного
обхода, чтобы не сканировать всю библиотеку дважды при распознавании.

### 4. Каталог Calibre-библиотеки не пишется приложением

`import_book` в Calibre-режиме возвращает ошибку read-only. UI получает режим
через `get_library_info` и скрывает кнопку «Добавить EPUB». Загрузка виртуального
каталога модулем `calibre/` выполняется только чтением (сканирование папок,
чтение `metadata.opf` и обложек).

### 5. Открытие во внешнем приложении через `open` crate

`open_book_in_system` находит BookFile у книги (kind=Book) и вызывает
`open::that(abs_path)` (системный обработчик по умолчанию). Альтернатива —
`tauri-plugin-shell`, но она требует настройки capability и лишней обвязки;
`open` — минимальная зависимость с теми же возможностями.

### 6. Разбор `metadata.opf` через `quick-xml`

`metadata.opf` — XML стандарта EPUB OPF, в нём `dc:title`, `dc:creator`,
`dc:subject`, `dc:language`, `meta[name="calibre:series"]`, `cover`. Используем
`quick-xml` (лёгкий, без тяжёлых зависимостей) со строгим fallback: если
`metadata.opf` отсутствует или не разбирается, название и автор извлекаются из
имён папок (`<Title> (id)` / имя папки автора). Альтернатива — `roxmltree`/ручной
парсинг: `quick-xml` проще для потоковой обработки, `roxmltree` удобнее для DOM,
но `metadata.opf` небольшой и потоковый разбор достаточен.

## Risks / Trade-offs

- [Производительность сканирования больших Calibre-библиотек] →
  Сканирование выполняется при старте; для тысяч книг это заметно, но приемлемо.
  Распознавание структуры ограничено глубинным поиском одного-двух уровней;
  полный обход делается только при построении каталога.
- [Нестандартные шаблоны путей Calibre] → Требование опирается на типовой
  двухуровневый шаблон и `metadata.opf`; при нестандартных шаблонах Calibre
  каталог может не распознаться. Это явное ограничение первой версии (см.
  Non-Goals).
- [Формат `metadata.opf` может отсутствовать] → fallback на имена папок
  (покрыто spec «Книга с метаданными» и «Книга без обложки»).
- [Открытие файла системным приложением в песочнице Tauri] → `open` работает
  на десктопе; при невозможности вернётся ошибка команды.
- [In-memory БД и память при очень больших каталогах] → Вся БД в памяти;
  для типовых книжных библиотек (<100k записей) допустимо, для сверхбольшой
  Calibre-библиотеки это trade-off осознанный (Non-Goals: без persist-индекса).

## Migration Plan

- Новая функциональность аддитивная; схема БД и структура собственной библиотеки
  не меняются, поэтому миграция данных не требуется.
- Правки ограничены: `Library` (режим), новый модуль `calibre/`, новые команды,
  фронтенд (`Library.svelte`, типы). Откат — удаление новых команд/ветки режима;
  старые сценарии (`cargo test`, импорт, чтение) остаются покрытыми без изменений.
